# Практика: исследование UI/UX

Дата: 2026-09-13. Объект: текущий dev, `/practice` и самостоятельные задачи.
Метод: независимые оценки A (`practice_design`, исходный код) и B
(`practice_detector`, статический скан), затем браузерная проверка основным агентом
и сопоставление с опубликованными рекомендациями. Это экспертное исследование;
наблюдений за учениками и доказанного эффекта изменений пока нет.

## Вывод

Каталог должен помогать выбрать подходящее упражнение, экран задачи — поддерживать
непрерывный цикл «прочитать → попробовать → получить помощь → проверить → продолжить».
Текущая реализация обеспечивает базовые действия, но слабо поддерживает выбор и
продолжение. Приоритет — структура, содержание и обратная связь.

Сохранить фирменные тёплую бумагу, чернильный текст, оранжевый акцент и спокойную
типографику infraege. Каталог использовать как рабочий список; условие — как
читательскую колонку с удобной формой ответа.

## Полезные практики и референсы

1. **Предлагать выбор, а не требовать знания идентификаторов.** College Board
   описывает банк с выбором раздела, навыка и сложности. Переносимый принцип для
   нас — осмысленная навигация по учебной задаче; экспорт тестов и учётные записи
   для этого не обязательны.
   [College Board](https://satsuite.collegeboard.org/practice/build-your-study-plan).
2. **Показывать главное сразу, второстепенное — по запросу.** Это подходит для
   дополнительных фильтров, справки и альтернативных языков. Условие и ответ
   остаются рядом, помощь легко обнаруживается.
   [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/).
3. **Выбирать поведение фильтров по сценарию.** Быстрый переключатель темы может
   обновлять список сразу; несколько мобильных фильтров удобно применить одной
   кнопкой. Сохранять контекст и не сдвигать экран во время выбора.
   [NN/g: User Intent Affects Filter Design](https://www.nngroup.com/articles/applying-filters/).
4. **Разделять помощь до ответа и объяснение после.** Khan Academy описывает
   пошаговые hints и rationales. Для нас: короткая идея, дальнейший шаг и полный
   разбор, когда для задачи действительно подготовлен такой материал. Помощь
   доступна добровольно без обязательной ошибочной попытки.
   [Khan Academy](https://blog.khanacademy.org/how-should-people-practice-on-khan-academy/).
5. **Обратная связь должна поддерживать понимание.** Подтверждение правильности
   полезно дополнять объяснением. Из одного неверного числа нельзя достоверно
   вывести причину ошибки; показывать диагностику только при наличии проверенного
   правила для конкретной задачи.
   [Retrieval Practice](https://www.retrievalpractice.org/faq).
6. **Доступные действия и статусы.** Результат проверки должен восприниматься без
   перемещения фокуса в длинный текст. Размер интерактивных целей оценивать по
   WCAG 2.2: минимум 24×24 CSS px либо предусмотренные исключения/расстояния;
   для главных мобильных кнопок проектно целиться примерно в 44–48 px.
   [W3C: Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html),
   [W3C: Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

## Предлагаемый интерфейс

Каталог: «Практика» → быстрый выбор «Все / №5 / №16» → дополнительные фильтры →
число найденных задач и выбранные ограничения → различимые строки задач.
Статусы решения обозначаются текстом и знаком, а не только цветом.

Задача: возврат к выбранному списку → компактный заголовок с номером ЕГЭ →
условие и файлы → поле с инструкцией формата + «Проверить» → короткий результат →
подсказка / разбор / ссылка на урок → следующая задача после успешного ответа.
Источник остаётся компактной метаинформацией. Ссылка на теорию ведёт на целый урок,
как ранее согласовано.

На desktop исходная гипотеза — одна читаемая основная колонка. Боковая панель
оправдана при достаточно длинных заданиях и реальной пользе; две независимо
прокручиваемые колонки не вводить автоматически. На мобильном сохранять линейное
чтение; закреплённую кнопку проверять с открытой клавиатурой и крупным текстом.

Тёплый фон и фирменная типографика сохраняются. Сетка фона под длинным условием
может стать слабее; формулы следует оформлять как математические выражения,
программный код — как код. Избыточные карточки и большие иллюстрации для каждой
из сотен задач не добавляют информации для выбора.

## Порядок проверки гипотез

1. Прототип списка, условия, ошибки и успеха на desktop/mobile; проверить на
   короткой формуле, длинном тексте, многоязычном коде и задании с файлом.
2. Исправить фильтры, различимость строк, отступы, инструкцию ответа и дублирование
   feedback. Сохранить исходные ответы и внутренние UUID.
3. Добавить продолжение и возврат с контекстом; отдельно определить достоверные
   статусы и фильтрацию по локальному прогрессу. Фильтр по прогрессу должен работать
   по всему банку, а не только по загруженной странице.
4. Развивать редакционное качество подсказок и разборов отдельной задачей.

Для проверки пригласить 5–6 учеников разного уровня и дать сценарии: найти
базовую задачу №16; после ошибки получить помощь; после успеха продолжить;
вернуться к выбранному списку. Измерять время выбора, лишние открытия,
успешность продолжения и понимание feedback. Это формативное исследование,
не статистическое доказательство роста учебных результатов. Сравнить исходный
интерфейс и прототип; проверить клавиатуру, увеличение текста и медленную сеть.

Сильные стороны: спокойная фирменная среда, линейное условие, доступные по желанию
подсказки, сохранение введённого ответа при ошибке, текстовые состояния, независимый
прогресс. Сохранить их в переработке.

Основная лишняя нагрузка: вспоминать идентификатор навыка, удерживать инструкцию
ответа до конца условия, заново выбирать фильтры. Начинающему трудно выбрать;
возвращающемуся ученику неудобно продолжать; мобильному приходится прокручивать
служебное введение и повторные варианты кода. Это экспертные гипотезы о последствиях
наблюдаемых решений, а не результаты пользовательских интервью.

Мелкие замечания: сложность в списке числовая, на задаче словесная; у списка нет
явного счётчика результатов. Полный аудит контраста, screen reader и производительности
не проводился. Статический детектор проверил 44 файла в пяти целевых каталогах,
вернул 0 замечаний; он не оценивает полезность структуры и качество объяснений.

Вопросы следующего этапа проектирования: какие признаки позволяют выбрать между
двумя задачами одного типа; какое действие нужно после успеха; какой минимум
информации нужен до открытия задачи. Исходная рекомендация — сначала проработать
непрерывный путь решения и компактный каталог в существующей айдентике.
