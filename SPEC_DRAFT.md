# Спецификация MVP — платформа подготовки к ЕГЭ по информатике

## 0. Контекст и принципы

Продукт закрывает нишу, не занятую ни платными школами (продают преподавателя, теория — приложение к урокам), ни бесплатными банками заданий (теория есть, но текстовая простыня без структуры), ни новыми AI-ботами (решают конкретную задачу, не учат понимать тему).

Три принципа, которые должны быть видны в каждом архитектурном решении ниже:

1. **Понимание, а не заучивание шаблонов.** Каждая тема объясняет *почему так*, а не только *делай так*. Практика привязана к теории, а не существует отдельным банком.
2. **Явные связи между темами.** Ученик должен видеть: «это задание опирается на тему X» и «прежде чем идти сюда, разберись с тем». Связи — часть модели данных, а не текст в статье.
3. **Инкрементальный запуск.** Нет этапа «сделать весь курс, потом выложить». Единица релиза — одна тема или один мини-курс, полностью готовые (теория + визуализация + практика + связи), а не общий каркас с пустыми разделами.

## 1. Границы MVP

**Входит в MVP:**
- 3–5 самых проблемных тем ЕГЭ (по номерам заданий) — полностью, с теорией, визуализацией и практикой.
- 1 мини-курс (рекомендация: Python — он закрывает больше всего номеров: 6, 8, 11, 14, 15, 16, 17, 18, 20–27, а не Excel, который закрывает точечно 2–3 задания на таблицы; начать с того, что даёт наибольший охват связей).
- Механизм связей «тема ЕГЭ ↔ урок мини-курса» (двусторонние ссылки, признак «требуется перед этим»).
- Публичные, индексируемые страницы тем и уроков (SSR/SSG) — это твой основной канал роста, закладывается с первого дня, а не добавляется потом.
- Практика по каждой теме: 5–10 заданий с проверкой ответа, без «умного» подбора сложности.
- Прогресс на уровне браузера (localStorage/аналог), без обязательной регистрации.

**Осознанно не входит в MVP** (важно зафиксировать, чтобы не расползаться):
- Аккаунты и синхронизация прогресса между устройствами.
- Полноценный тренажёр-пробник ЕГЭ с таймером на весь вариант.
- Платные функции любого вида.
- AI внутри продукта (только как инструмент автора при подготовке контента).
- Мини-курс Excel и остальные темы ЕГЭ — во второй волне, по той же структуре, что и первая.

## 2. Архитектура контента (ключевая часть спецификации)

Это самое важное архитектурное решение: **контент — это структурированные данные с типизированными связями, а не набор HTML/MDX-страниц без метаданных.** Иначе фича «показать связь между темами» превратится в ручную расстановку ссылок в тексте, которая не масштабируется и не даёт нормального UI навигации (граф связей, «что пройти сначала» и т.д.).

### 2.1 Сущности

**Topic** (тема ЕГЭ, привязана к номеру задания)
```
id: slug (например "graphs-matrix-table")
task_numbers: [1, 3]        // может закрывать несколько номеров
title
summary                     // 1-2 предложения для превью и meta description
content_blocks: [ContentBlock]
prerequisites: [topic_id | course_lesson_id]   // что нужно пройти раньше
mastery_threshold: 0.8      // доля верных ответов в практике, необходимая для статуса "усвоено" (см. раздел 9, п.4 — Bloom mastery learning)
presentation_mode: worked_example_first | productive_failure_first  // см. раздел 9, п.1 и п.5
related_topics: [topic_id]  // не обязательные, но полезные связи
practice_task_ids: [task_id]
status: draft | review | published
```
`prerequisites` — это не булев чек-лист «открыл страницу», а ссылка на mastery-статус связанной темы/урока: тема считается пройденной для целей разблокировки только при достижении `mastery_threshold` в практике, а не при факте прочтения (обоснование — раздел 9, п.4).

**Course** (мини-курс: Python, позже Excel и др.)
```
id: slug ("python-basics")
title
lessons: [CourseLesson]
```

**CourseLesson**
```
id: slug ("python-loops")
course_id
title
content_blocks: [ContentBlock]
unlocks_topics: [topic_id]   // связь в обратную сторону: после этого урока — вот эти темы ЕГЭ
practice_task_ids: [task_id]
status: draft | review | published
```

**ContentBlock** (типизированный, не просто rich text — это то, что даёт "осмысленную" подачу вместо простыни текста)
```
type: text | diagram | code_example | worked_example | completion_exercise | productive_failure_prompt | callout | video_embed
data: (зависит от типа)
```
Важно: `diagram` — это не картинка-файл, а декларативные данные (например конфиг для рендера SVG-схемы графа/автомата/таблицы кодирования), чтобы:
- при желании позже сделать интерактив (подсветка вершины по клику) без переделки контент-модели;
- контент оставался текстовым (git-friendly, диффится, редактируется без графического редактора).

Три новых типа блока добавлены не произвольно, а как прямое следствие принципов из раздела 9:
- `worked_example` — полностью разобранный пример, для начала изучения принципиально нового материала.
- `completion_exercise` — задача с частично заполненным решением, промежуточный шаг между worked example и полностью самостоятельной задачей.
- `productive_failure_prompt` — задача, которую ученику предлагают решить до объяснения теории (используется только при `presentation_mode: productive_failure_first`, то есть когда тема опирается на уже знакомые ученику смежные понятия).

**Task** (единица практики)
```
id
topic_ids: [topic_id]        // может относиться к нескольким темам
statement
checker_type: exact_match | numeric_tolerance
answer_variants: [string]    // все допустимые написания верного ответа, не одно значение (см. раздел 11.1)
numeric_tolerance: float     // только для checker_type: numeric_tolerance
interaction_type: production | recognition   // приоритет — production (см. раздел 9, п.3)
explanation                  // разбор решения, тоже как content_blocks — полноценный worked example, не короткая строка "правильный ответ: X" (раздел 9, п.6)
difficulty: 1-3
is_interleaving_eligible: bool  // может попадать в смешанные подборки из нескольких тем (раздел 9, п.3); включается по умолчанию для published-задач
```

### 2.1.1 Диаграмм-движок — решение и обоснование

**Решение: собственная лёгкая библиотека React-компонентов, рендерящих чистый SVG из декларативных данных — не готовая diagram-библиотека (React Flow, Cytoscape, D3) и не набор картинок.**

Почему не готовая библиотека, хотя они существуют и активно поддерживаются:
- React Flow и Cytoscape.js спроектированы для *интерактивных, редактируемых* графов (перетаскивание узлов, построение связей на лету) — это другой набор задач, чем «показать статичную схему с подсветкой одного элемента». Даже React Flow, у которого есть официальная поддержка SSR, требует явно фиксировать `width`/`height` каждого узла для серверного рендера — то есть всё равно сводится к ручному заданию геометрии, но поверх более тяжёлой и заточенной под другое библиотеки.
- Любая внешняя diagram-библиотека диктует свою форму данных (свой формат node/edge), из-за чего кастомные примитивы, которые нужны именно для педагогики — `highlight` (раздел 9.2, signalling principle) и подписи-на-элементе (split-attention effect) — придётся либо обходить хаками поверх чужого API, либо всё равно писать свой слой поверх библиотеки. Раз всё равно нужен свой слой — логичнее не тащить лишнюю зависимость и её вес в бандл.
- Собственные компоненты — это чистый SVG-рендер из данных, без клиентского JS вообще (кроме будущей точечной интерактивности) — идеально ложится на требование «страница читаема без JS» (раздел 6) и на Core Web Vitals.

**Как это устроено:**
- Координаты элементов (узлов графа, ячеек таблицы) — часть данных темы, а не результат работы layout-алгоритма в рантайме. Это осознанный выбор: раз контент правится вручную после генерации AI (раздел 2.2), автор в любом случае визуально проверяет и поправляет диаграмму — удобнее поправить два числа `x`/`y` в данных, чем разбираться, почему авто-layout расположил вершины неудачно. Как вспомогательный **авторский** (не рантайм) инструмент можно один раз прогнать данные через библиотеку раскладки графов (например `dagre` или `elkjs`) как одноразовый CLI-скрипт, который просто подставит стартовые координаты в JSON — после чего библиотека выходит из зависимостей проекта.
- Для табличных диаграмм (кодировочные сетки, таблицы истинности) — используется семантический HTML `<table>` с CSS-подсветкой ячеек, а не SVG. Это одновременно проще и лучше для доступности (раздел 6) — скринридер нативно понимает HTML-таблицу, а произвольный SVG с текстом внутри — нет.
- Для графов/автоматов — общий набор SVG-примитивов: `node`, `edge`, `arrow`, `label`, `highlight`. Каждая диаграмма — JSON-объект с типом (`graph`, `automaton`, `bit-grid` и т.д.) и списком элементов этого набора; рендер-компонент один на тип диаграммы, переиспользуется всеми темами этого типа.
- Точечная интерактивность в будущем (подсветка вершины по клику) добавляется поверх уже отрендеренного на сервере SVG через progressive enhancement — обработчики событий довешиваются на клиенте, сам SVG не пересоздаётся заново через клиентскую библиотеку.

### 2.2 Как хранить контент технически

**Монорепозиторий** — frontend, backend и контент живут в одном git-репозитории, не разнесены по отдельным репо. Для одного разработчика это даёт один CI-пайплайн, одну историю версий и не требует синхронизации submodule/нескольких репо при каждом деплое. Разносить контент в отдельный репозиторий имело бы смысл только при подключении внешних авторов без доступа к коду — сейчас это не так, а если понадобится позже, вынести папку `content/` в отдельный репозиторий — дешёвая операция (`git filter-repo`/новый remote), не требующая менять модель данных.

Ориентировочная структура:
```
/
  apps/
    web/            — TanStack Start (frontend)
    api/            — FastAPI (backend)
  content/
    topics/         — *.mdx/*.json по темам ЕГЭ
    courses/        — мини-курсы (python-basics/ и т.д.)
  infra/
    docker-compose.yml
    nginx/
  scripts/          — CI-валидация связей контента (раздел 2.2), деплой-скрипт (раздел 10.3)
```

Рекомендация: **контент как код (content-as-code)**, не как записи в админке с первого дня.

- Темы и уроки — файлы `*.mdx` или `*.json` в отдельном content-репозитории/папке, с frontmatter под поля модели выше.
- Это даёт: версионирование через git, возможность ревьюить AI-сгенерированные черновики через diff (ты генерируешь черновик темы через LLM → правишь → коммитишь), простую CI-проверку (например, скрипт валидирует, что все `prerequisites` и `related_topics` ссылаются на существующие id — иначе сборка падает и битые связи не уедут в прод).
- На этапе, когда появится нужда в динамическом редактировании без деплоя (например, если подключишь других авторов) — мигрировать в БД. Для одного автора на старте git-контент быстрее и надёжнее.

Данные пользователя (прогресс, ответы) — отдельно, в БД с первого дня (см. ниже), это не контент, это состояние.

## 3. Пользовательские сценарии (MVP)

1. **Заход через поиск на страницу конкретной темы** («ЕГЭ информатика задание 1 графы и таблицы теория») → видит теорию с визуализацией → внизу практика по теме → если тема опирается на мини-курс, видит явный блок «Эта тема легче даётся, если понимать [Python: списки] → перейти».
2. **Заход в мини-курс** (например, кто-то целенаправленно учит Python) → проходит уроки последовательно → после урока видит «Теперь ты готов к темам ЕГЭ: [список], попробуй».
3. **Практика без предварительного чтения теории** → если ошибается — ссылка «непонятно почему? → к теории».
4. **Возврат на сайт** → localStorage помнит, какие темы/уроки отмечены пройденными, показывает прогресс-бар без регистрации.

## 4. Технический стек

**Frontend: React + TanStack Start**
- SSR/SSG обязателен — органический поиск — основной канал роста, страницы тем должны быть полностью отрендерены на сервере с корректными `<title>`/`meta description`/`og:*`, без клиентского дорендера контента.
- File-based роутинг TanStack Start хорошо ложится на структуру `/theory/{topic-slug}`, `/course/{course-slug}/{lesson-slug}`.
- Статическая генерация (build-time) подходит для контента тем/уроков, раз он хранится как git-контент и меняется только через деплой — не нужен SSR на каждый запрос для этих страниц, что снижает нагрузку и стоимость хостинга при росте трафика.

**Backend: Python/FastAPI**
- На MVP backend нужен для узкого набора вещей, не для отдачи контента (тот генерируется статически):
  - Проверка ответов практики (`POST /api/tasks/{id}/check`).
  - Отдача графа связей тем/уроков, если понадобится API для клиентской навигации (или это тоже можно собрать в статические JSON на этапе билда — решить при реализации, не усложнять заранее).
  - В будущем — эндпоинты для аккаунтов/прогресса/платных фич.
- БД (Postgres) на MVP хранит по минимуму: результаты практики (если решишь агрегировать анонимную аналитику — какие задания чаще всего решают неверно, это ценные данные для приоритизации следующих тем).

**Важно не размывать границу:** контент — статика/git, состояние пользователя — API/БД. Если эти два слоя перемешать с первого дня (например, темы в БД через админку), скорость итерации по контенту резко упадёт, а именно скорость выпуска тем — то, что определяет, наберёшь ли ты трафик раньше, чем конкуренты допилят свои AI-боты до полноценной теории.

## 5. SEO-требования (нефункциональные, но критичные)

- URL по паттерну `/theory/zadanie-{n}-{slug}` — соответствует тому, как реально ищут («ЕГЭ информатика задание 7 теория»), и как уже ранжируются конкуренты (ctege.info, Экзамер) — не изобретать свою таксономию URL.
- Каждая страница темы — уникальные title/description, сгенерированные из полей `title`/`summary`, а не общий шаблон.
- Sitemap.xml генерируется автоматически из списка published тем/уроков при билде.
- Structured data (schema.org `LearningResource` или `FAQPage` для практики) — опционально, но дёшево добавить сразу, пока структура контента и так типизирована.

## 6. Нефункциональные требования

- Mobile-first — с учётом того, что старшеклассники в основном заходят с телефона.
- Страница темы должна открываться и быть читаемой без JS (SSR-контент, интерактивность — прогрессивное улучшение), это и для SEO, и на случай медленного мобильного интернета в школе.
- Без обязательной регистрации на MVP — намеренно снижает порог входа, учитывая что монетизации пока нет и приоритет — трафик и удержание, а не сбор лидов.
- **Core Web Vitals — измеримые пороги, не общие слова:** LCP < 2.5s, CLS < 0.1, INP < 200ms на мобильном 4G-профиле. Раз SEO — ключевой канал роста (раздел 5), эти метрики влияют на ранжирование напрямую, а не только на субъективное удобство. Архитектура уже работает на это (SSR/SSG контента, отсутствие тяжёлых diagram-библиотек — раздел 2.1.1) — но стоит явно проверять по факту (Lighthouse/PageSpeed Insights) на каждую опубликованную тему, а не полагаться на то, что архитектура «сама» это даёт.
- **Базовая доступность (a11y):** каждый `diagram`-блок графового/автоматного типа обязан иметь `aria-label`/`<title>` внутри SVG с текстовым описанием сути схемы; табличные диаграммы рендерятся семантическим HTML `<table>` (раздел 2.1.1), что даёт доступность «бесплатно», без дополнительной разметки. Полный WCAG-аудит не входит в MVP — это точечное требование, чтобы контент, сделанный ставкой на визуальную подачу, не был буквально недоступен части аудитории.

## 7. Поэтапный план релиза

**Этап 0 — фундамент.** Модель контента (типы, схема frontmatter), базовый рендер ContentBlock (включая diagram-блок хотя бы в статичном SVG-варианте), скрипт валидации связей.

**Этап 1 — первая тема целиком.** Одна тема ЕГЭ (рекомендация: именно граф+таблица — тема с максимальной подтверждённой болью) в финальном качестве: текст, диаграмма, практика, meta/SEO. Это эталон, по которому дальше штампуются остальные.

**Этап 2 — ещё 2-4 темы + первые уроки Python-курса.** Первая проверка связей «тема ↔ урок курса» на реальном контенте, а не в теории.

**Этап 3 — публичный запуск MVP.** Индексация, сбор первых органических пользователей, наблюдение за метриками (какие темы читают, где отваливаются в практике) — это входные данные для приоритизации следующих тем, а не гадание.

**Этап 4+ (после трафика)** — второй мини-курс (Excel), аккаунты и синхронизация прогресса, затем платные фичи поверх уже работающей бесплатной базы — без AI внутри продукта до этого момента, как и обозначено.

## 9. Принципы контента на основе learning science — обязательны при генерации через AI

Полное обоснование каждого пункта (с источниками) — в отдельном документе `learning-science-principles.md`. Здесь — версия, привязанная к полям модели данных из раздела 2, обязательная к соблюдению при любой генерации контента через AI, независимо от того, кто именно ревьюит результат.

Это не рекомендации на будущее — они уже отражены в модели данных выше (`mastery_threshold`, `presentation_mode`, `worked_example`/`completion_exercise`/`productive_failure_prompt`, `interaction_type`, `is_interleaving_eligible`). Раздел ниже объясняет, почему эти поля появились, и что конкретно должен делать AI-агент при заполнении каждого из них.

### 9.1 Порядок подачи внутри темы (worked-example effect + expertise reversal)

Для принципиально нового материала (ученик впервые встречает эту нотацию/концепцию) — тема обязана открываться блоком `worked_example`, а не сразу задачей на самостоятельное решение. Порядок: `worked_example` → `completion_exercise` → полностью самостоятельная задача из `practice_task_ids`.

Если тема логически продолжает уже знакомые ученику концепции (проверяется по `prerequisites` — они уже усвоены) — допустим `presentation_mode: productive_failure_first`: тема открывается блоком `productive_failure_prompt` (задача до объяснения, с расчётом на то, что ученик, скорее всего, не решит), и только затем идёт теория, которая явно объясняет, почему интуитивный подход не сработал.

**Указание для AI-агента:** при генерации темы — сначала явно определи `presentation_mode` по признаку «опирается ли тема на уже усвоенные `prerequisites`», и только затем генерируй content_blocks в соответствующем порядке. Не начинай тему с самостоятельной задачи, если `presentation_mode` не установлен в `productive_failure_first`.

### 9.2 Визуальная подача (Mayer + split-attention)

Каждый `diagram`-блок обязан:
- размещать подписи и обозначения прямо на элементах схемы, а не отдельным текстовым блоком до/после (split-attention effect);
- визуально выделять (цветом/обводкой) именно тот элемент, о котором идёт речь в соседнем тексте (signalling principle), а не оставлять все элементы визуально равнозначными;
- не дублировать текстом то, что уже однозначно показано на схеме, и не включать декоративные элементы, не несущие смысловой нагрузки (redundancy / coherence principles).

**Указание для AI-агента:** при генерации `diagram`-блока — для каждого элемента схемы явно сопоставь, какому предложению текста он соответствует, и не создавай элементов «для полноты картины», если на них нет прямой смысловой ссылки в тексте.

### 9.3 Дизайн практики (testing effect + interleaving)

Задачи в `practice_task_ids` должны в первую очередь иметь `interaction_type: production` (ввод ответа/числа/кода), а не `recognition` (выбор из вариантов) — production сильнее задействует retrieval-механизм, который и даёт эффект обучения. `recognition` допустим точечно, если формат задачи объективно этого требует (например, задачи ЕГЭ, где сам формат — выбор из вариантов).

Все опубликованные задачи по умолчанию помечены `is_interleaving_eligible: true`, чтобы после накопления нескольких тем система могла собирать смешанные подборки задач из разных тем — это не опциональная фича для ученика, а обязательное поведение системы (ученики систематически недооценивают эффективность перемешанной практики, поэтому она не должна быть настройкой «по желанию»).

**Указание для AI-агента:** при генерации задач — формулируй условие так, чтобы ответ вводился, а не выбирался, если формат задания ЕГЭ это допускает.

### 9.4 Порог перехода (mastery learning)

`mastery_threshold` у темы (по умолчанию 0.8) — это не декоративное поле, а условие разблокировки следующей темы через `prerequisites`. Тема считается пройденной для целей навигации/прогресса только при достижении этого порога в практике, не по факту открытия страницы.

**Указание для AI-агента:** при генерации новой темы — всегда заполняй `mastery_threshold` осознанно (не оставляй дефолт бездумно), понижая его только для тем с объективно небольшим набором задач, где 80% недостижимы из-за малой выборки.

### 9.5 Глубина разбора ошибки (feedback depth)

Поле `explanation` в Task — не короткая строка «правильный ответ: X», а полноценный `worked_example`-подобный разбор: почему это верный ответ и в чём именно ошибочна типичная логика, которая приводит к неверному. Немедленность сообщения «верно/неверно» уже гарантирована UX (раздел 4, эндпоинт `/api/tasks/{id}/check`) — усилие нужно вкладывать в глубину `explanation`, а не в скорость его показа.

**Указание для AI-агента:** при генерации `explanation` — не ограничивайся указанием правильного ответа; явно опиши наиболее вероятную ошибку в рассуждении, которая приводит к неверному ответу, и почему она неверна.

### 9.6 Общий контракт при генерации контента

При каждой генерации Topic/CourseLesson/Task через AI — черновик обязан быть проверен по чек-листу из документа `learning-science-principles.md` (раздел 8 того документа) до перевода в статус `review`. Это должно быть частью промпта, который используется для генерации черновиков (то есть сам промпт для LLM обязан включать этот чек-лист как явное требование, а не полагаться на то, что модель воспроизведёт эти принципы «по умолчанию»).

## 10. Хостинг, деплой и окружения

Исходные данные: один VPS (hip.hosting) на старте, домен и CDN — reg.ru, Nginx как gateway, тестирование локально без отдельного preview/staging-стенда.

### 10.1 Топология на VPS

Всё на одном сервере через Docker Compose — это осознанно, раз задача «ничего лишнего и затратного» на старте:
- **Nginx** — единственная точка входа с наружи (80/443), реверс-прокси и раздача статики.
- **Frontend (TanStack Start)** — билд статики (раздел 2.1.1/4: контент пререндерится на этапе сборки) кладётся в volume, который Nginx отдаёт напрямую по `location /` — не через прокси на Node-процесс, если он не нужен для чисто статических страниц тем. Если часть маршрутов всё же требует SSR на каждый запрос — под них отдельный `location`, проксируемый на Node-процесс фронтенда.
- **Backend (FastAPI/Uvicorn)** — отдельный контейнер, доступен для Nginx по внутренней docker-сети, наружу не смотрит напрямую.
- **Postgres** — отдельный контейнер, на том же VPS, данные в volume с регулярным бэкапом (см. 10.3).
- **Observability-стек** (раздел 12) — те же контейнеры на этом VPS на старте; при росте нагрузки это первое, что можно вынести на отдельный маленький VPS, не трогая основной стек.

### 10.2 Nginx и CDN — как они сочетаются, а не конфликтуют

Конфликта в классическом смысле нет, если правильно разделить зоны ответственности — CDN reg.ru работает как edge-кэш перед источником (origin), а не вместо Nginx:

- Домен указывает (через DNS/CNAME на стороне reg.ru) на CDN, а CDN, в свою очередь, обращается за оригиналом к твоему VPS с Nginx — это классическая схема origin-pull, а не что-то специфичное для reg.ru.
- Nginx на VPS остаётся источником истины и продолжает отдавать статику и проксировать API как обычно — просто теперь не каждый запрос браузера доходит до него, часть отдаётся из кэша на edge-серверах CDN, ближе к пользователю.
- Ключевое условие, чтобы это работало правильно: Nginx должен выставлять корректные `Cache-Control`/`ETag` заголовки для статики (билд фронтенда, изображения) — именно на эти заголовки ориентируется CDN, решая, что и насколько долго кэшировать. Для файлов с хэшем в имени (типичный вывод сборки TanStack Start/Vite) — `Cache-Control: public, max-age=31536000, immutable`, поскольку смена содержимого всегда даёт новое имя файла.
- Динамические запросы — эндпоинт проверки ответа (`/api/tasks/{id}/check`) — не должны кэшироваться CDN. Практически: вынести backend на отдельный поддомен (например `api.<домен>`), который либо не подключён к CDN вовсе, либо подключён с явным правилом «не кэшировать» для этого пути — так CDN физически не тронет динамику, и не будет нужно тонко настраивать исключения на уровне одного домена.
- SSL: сертификат нужен и на CDN (для домена, который видит браузер), и на origin (Nginx на VPS, чтобы соединение CDN → origin было тоже зашифровано) — обычно это Let's Encrypt на стороне Nginx (через certbot) плюс то, что предоставляет CDN на своей стороне для внешнего домена.

Насчёт выбора reg.ru CDN вместо Cloudflare — раз аудитория продукта целиком в РФ, edge-точки российского CDN дают меньшую задержку для целевых пользователей и не создают риска зависимости от иностранного edge-провайдера, который для части российской аудитории/сетей исторически имел проблемы со стабильностью доступа. Cloudflare стоит держать в уме как опцию только если аудитория когда-нибудь станет международной — сейчас это не тот случай.

### 10.3 Окружения и деплой без отдельного staging

Раз явно решено не тратиться на отдельный превью-стенд — тестирование на localhost должно максимально точно повторять прод, иначе разница окружений всё равно себя проявит уже на проде:

- Тот же `docker-compose.yml` (или его локальный вариант с минимальными переопределениями через `docker-compose.override.yml`) используется и локально, и на VPS — не два независимых способа поднять проект.
- Деплой — простой скрипт или GitHub Actions на пуш в `main`: собрать образы → скопировать/запушить на VPS → `docker compose up -d --build`. Это не требует отдельного стенда, но даёт воспроизводимость и защиту от «а на моей машине работало» — стоит сделать это с первого дня, раз ручной SSH+git pull на проде — та же самая работа, но без истории и отката.
- Резервное копирование Postgres — простой cron с `pg_dump` в отдельную директорию на том же VPS (и по возможности — периодическая выгрузка бэкапа за пределы VPS, например в S3-совместимое хранилище reg.ru/облако, чтобы не потерять данные при отказе самого VPS). Это не про масштаб, а про то, что на единственном сервере без бэкапа один сбой диска стирает и контент базы, и накопленную аналитику.

## 11. Защита и корректность практики

### 11.1 Нормализация проверки ответов

`answer_variants` (раздел 2.1) — не одна строка, а список допустимых написаний правильного ответа, потому что для ЕГЭ-формата однозначного «единственно верного текста» часто не существует. Правила нормализации перед сравнением (применяются к обеим сторонам — введённому ответу и каждому варианту из `answer_variants`):

- Обрезка пробелов по краям и схлопывание внутренних множественных пробелов.
- Регистронезависимое сравнение для буквенных ответов.
- Нормализация «ё»/«е» — типичный источник ложных «неверно» для русскоязычного ввода.
- Числовые ответы: эквивалентность форматов («12», «12.0», «12,0» — учитывая, что часть пользователей будет по привычке ставить запятую как десятичный разделитель, а не точку) — нормализовать к единому числовому виду перед сравнением, а не сравнивать как строки.
- Для `checker_type: numeric_tolerance` — сравнение с допуском `numeric_tolerance` (для задач, где верный ответ — вычисляемое значение с плавающей точкой), а не точное совпадение.
- Для ответов-списков значений (если формат задания это подразумевает) — явно фиксировать в самой задаче, важен ли порядок, а не полагаться на угадывание при проверке.

**Указание для AI-агента:** при генерации задачи — заполнять `answer_variants` не одним значением по умолчанию, а явно продумывать, в каких альтернативных корректных форматах ученик может ввести тот же самый верный ответ.

### 11.2 Защита публичного checker-эндпоинта

`/api/tasks/{id}/check` не требует аккаунта — открытая цель для скрапинга банка ответов автоматизированным перебором. Раз Nginx и так уже стоит перед backend (раздел 10.1) — рациональнее ограничивать на этом уровне, а не добавлять отдельную зависимость в FastAPI:

```
limit_req_zone $binary_remote_addr zone=checker:10m rate=20r/m;

location /api/tasks/ {
    limit_req zone=checker burst=5 nodelay;
    proxy_pass http://backend;
}
```
Ориентир — 20 запросов в минуту на IP с коротким burst: с запасом покрывает реальное использование одним учеником (он физически не решает 20 задач в минуту) и режет автоматизированный перебор. Точную цифру стоит поправить по факту, ориентируясь на реальные логи после запуска, а не считать зафиксированной раз и навсегда.

## 12. Наблюдаемость: аналитика, метрики, ошибки

Вводная: всё self-hosted, всё на том же VPS (раздел 10.1) на старте, приоритет — минимальный расход ресурсов и наличие UI, без завязки на платные облачные сервисы.

**Веб-аналитика — Umami.** Лёгкий self-hosted инструмент, использует ту же Postgres (можно завести отдельную БД в уже поднятом контейнере, не разворачивать вторую СУБД), даёт готовый UI и не хранит избыточно детальные персональные данные по умолчанию — что попутно снижает объём персональных данных, которые вообще приходится обрабатывать (см. раздел 13.1). Конкретные события, которые стоит трекать с первого дня публикации (раздел 7, этап 3 явно на них опирается): просмотр темы, старт практики по теме, номер задачи, на которой ученик прекратил попытки — этого достаточно, чтобы приоритизировать следующие темы по данным, а не на глаз.

**Метрики самого сервера — Beszel.** Лёгкая альтернатива Netdata: агент занимает единицы мегабайт ОЗУ против сотен у Netdata, при этом даёт то же самое «жив ли сервер, сколько CPU/RAM/диска съедено» с готовым UI. На единственном небольшом VPS это ощутимая разница в занятых ресурсах при сопоставимой пользе. Netdata стоит держать в уме как апгрейд, если понадобится посекундная детализация метрик, но не как стартовый выбор.

**Доступность извне — Uptime Kuma.** Проверяет, что сайт и API отвечают, следит за сроком действия TLS-сертификата, шлёт алерты в тот же Telegram, где уже будет канал обратной связи (раздел 14) — то есть не появляется отдельный канал уведомлений, используется уже существующий. Важная оговорка: раз это единственный VPS, при полном падении самого сервера Kuma падает вместе с ним и алерт не придёт — это принимаемое ограничение на старте (а не то, что нужно решать прямо сейчас через второй сервер), но стоит явно держать в уме, а не считать, что мониторинг покрывает и этот случай тоже.

**Ошибки бэкенда — не Sentry, а прямой Telegram-алерт.** Полноценный self-hosted Sentry (или даже облегчённый GlitchTip) — это дополнительная СУБД/очередь и заметный для единственного маленького VPS расход ресурсов ради функциональности, которая на этом масштабе избыточна. Вместо этого: middleware в FastAPI, который на необработанном исключении/5xx-ответе отправляет сообщение через Telegram Bot API в тот же служебный канал — это буквально несколько строк кода, ноль дополнительных сервисов, и решает именно ту проблему, которая явно сформулирована («узнать о падении иначе, чем от случайной жалобы»). Если проект вырастет настолько, что нужна будет история ошибок с трассировками, а не просто «что-то упало» — тогда это осознанный апгрейд до GlitchTip, а не решение по умолчанию сейчас.

**По поводу переиспользуемого инструмента для всех твоих проектов** — то, что ты описал (одно место, куда стекаются метрики/аналитика/fail2ban с разных проектов), не обязательно писать самому: Beszel и Uptime Kuma оба изначально спроектированы как одна панель, наблюдающая за множеством серверов/эндпоинтов одновременно, а не только за одним. Практический вывод: имеет смысл поднять **один** общий инстанс Beszel + Uptime Kuma (на этом же VPS на старте, или на отдельном маленьком VPS позже) и подключать к нему агентов/проверки от каждого нового проекта — тогда единая точка входа получается бесплатно, без написания своего дашборда. Разработку собственного UI для этого стоит рассматривать только если конкретно не хватит существующих UI этих инструментов на практике — а не проектировать заранее.

## 13. Юридические требования (РФ)

Ниже — ориентир, на что стоит обратить внимание, не юридическая консультация; перед запуском для сайта, ориентированного на школьников, стоит свериться с юристом хотя бы по 152-ФЗ и 436-ФЗ пунктам ниже — стоимость ошибки (штраф, предписание РКН) заметно выше стоимости консультации.

### 13.1 152-ФЗ — персональные данные

Даже без аккаунтов на MVP self-hosted аналитика (раздел 12) и логи Nginx технически обрабатывают IP-адреса, которые российская практика применения 152-ФЗ трактует как персональные данные. Из этого следует:
- **Уведомление в Роскомнадзор об обработке персональных данных**, как правило, требуется подать до начала обработки — практически до старта аналитики/логирования, а не постфактум; в законе есть исключение для обработки без средств автоматизации, но self-hosted аналитика и серверные логи под него не подпадают.
- **Локализация данных** (ст. 18 152-ФЗ) — первичный сбор персональных данных граждан РФ должен происходить на серверах, физически расположенных в России. Выбор VPS у hip.hosting уже работает в правильную сторону, но стоит явно проверить, что дата-центр физически находится в РФ (а не просто у провайдера с российским брендом есть площадки за рубежом), а не полагаться на название хостера.
- **Минимизация сбора данных снижает объём обязательств** — раз Umami по умолчанию не хранит сырые IP постоянно (агрегирует и не оставляет привязки к конкретному человеку), это не только техническое решение, но и прямое снижение юридической нагрузки — стоит явно проверить настройки анонимизации при разворачивании, а не полагаться на дефолт вслепую.
- На сайте нужна **страница «Политика обработки персональных данных»** — минимальное, но обязательное требование при любой обработке ПДн, включая аналитику.

### 13.2 436-ФЗ — возрастная маркировка информационной продукции

Закон предусматривает исключение для продукции с научной, научно-технической и образовательной направленностью (ст. 1, 11 436-ФЗ) — учебная теория по информатике по духу закона под это исключение, скорее всего, подпадает. Тем не менее, простая возрастная маркировка (например «12+» или «16+» — конкретную категорию имеет смысл определить вместе с юристом, а не гадать) — распространённая практика даже для явно образовательных сайтов, снимающая вопрос при формальной проверке, и стоит заложить место под неё в футере/на главной с первого релиза, а не добавлять по факту предписания.

### 13.3 Что дополнительно стоит иметь на сайте

- Простая страница «Пользовательское соглашение» (условия использования бесплатного сервиса) — не жёстко обязательна на этом масштабе, но снижает риски при любых будущих спорах и дёшево делается сразу, пока страниц на сайте мало.
- Про онлайн-кассы/54-ФЗ и связанные требования беспокоиться рано — они возникают только с появлением платежей (раздел 8), не на MVP-этапе.

### 13.4 Оригинальность контента — не только этическое, но и юридическое требование

Раз рост строится на SEO и уникальности контента (раздел 5), тексты тем и задачи из `practice_task_ids` должны быть собственного авторства/переформулированы, а не скопированы дословно из ФИПИ, sdamgia или kpolyakov.spb.ru — иначе есть прямой риск конфликта с этими площадками, а не только вопрос добросовестности. Это же требование дублируется в чек-листе Definition of Done (раздел 16) как отдельная точка проверки перед публикацией — чтобы оно не осталось декларацией, а реально проверялось на каждой теме.

## 14. Обратная связь от пользователей

Ссылка в футере/на страницах тем, ведущая в Telegram-канал/группу (или VK-группу) — свободная форма сообщений о проблемах, без отдельной формы обратной связи на сайте и без интеграции в код. Нулевая стоимость и нулевая сложность реализации, соответствует принципу MVP «ничего лишнего» — при этом уже даёт канал, который переиспользуется и для алертов мониторинга (раздел 12), не создавая отдельной инфраструктуры под саму обратную связь.

## 15. Не-цели (явно зафиксировано, чтобы не переусложнить раньше времени)

- **i18n/локализация** — продукт полностью на русском языке, аудитория исключительно русскоязычная (ЕГЭ — экзамен российской системы образования); необходимости в мультиязычности нет и не предвидится.
- **Полноценный поиск по сайту** — пока тем меньше десятка, обычная навигация по номерам заданий и разделам достаточна; добавить, когда объём контента оправдает отдельный поисковый UI.

## 16. Definition of Done — чек-лист перед переходом в `published`

Раздел 9.6 фиксирует, что черновик темы/задачи проверяется по педагогическому чек-листу из `learning-science-principles.md` — но это покрывает только подачу материала, не покрывает фактическую корректность и юридическую чистоту. Ниже — полный набор проверок, которые должны пройти до перевода статуса `draft`/`review` в `published`. Смысл именно в чек-листе, а не в общих словах «проверить перед публикацией» — чтобы первая тема, сделанная в первый день, не стала неявным (и непроверенным по всем пунктам) эталоном для всех последующих.

**Педагогика (раздел 9):**
- [ ] Порядок content_blocks соответствует `presentation_mode` темы (worked example / productive failure — раздел 9.1).
- [ ] В diagram-блоке нет элементов без прямой смысловой ссылки в тексте, ключевые элементы визуально выделены (раздел 9.2).
- [ ] Задачи используют `interaction_type: production`, кроме случаев, где сам формат ЕГЭ требует выбора варианта (раздел 9.3).
- [ ] `mastery_threshold` осознанно выставлен, не оставлен дефолтом бездумно (раздел 9.4).
- [ ] `explanation` каждой задачи — содержательный разбор с объяснением типичной ошибки, а не строка «правильный ответ: X» (раздел 9.5).

**Фактическая корректность:**
- [ ] Математика/логика в `worked_example` и `completion_exercise` проверена человеком вручную, а не принята на веру из AI-черновика.
- [ ] Все `answer_variants` каждой задачи реально протестированы через checker локально, включая нормализацию (раздел 11.1: ё/е, запятая/точка, обрезка пробелов) — не только «выглядит правильным» в тексте задачи.
- [ ] Данные diagram-блока визуально проверены в браузере (не только как JSON) — расположение элементов, читаемость подписей.

**Технически (раздел 2.2):**
- [ ] `prerequisites` и `related_topics` ссылаются на существующие id — проходит CI-валидацию связей.
- [ ] Заполнены `title`/`summary` для корректных meta-тегов (раздел 5) — не заглушки вида «TODO».
- [ ] diagram-блок графового/автоматного типа имеет `aria-label`/`<title>` (раздел 6).

**Юридически (раздел 13):**
- [ ] Текст темы и формулировки задач не являются близким пересказом источника — переформулированы самостоятельно (раздел 13.4).

Чек-лист стоит хранить рядом с контентом (например, как шаблон PR при добавлении новой темы), а не только в этом документе — чтобы прохождение по пунктам было явным действием при каждом ревью, а не тем, что подразумевается по умолчанию.
