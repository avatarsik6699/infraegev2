**Когда функция обращается к себе дважды, одни и те же значения вычисляются много раз; запоминание убирает повторы, а длинная цепочка вызовов — другая проблема с другим решением.** Здесь же — перебор аргументов: сколько n дают нужное значение или какое n наименьшее. Перебором решаются 7 задач подборок, в том числе задачи СтатГрада 2025 года, а запоминание нужно и при аргументах в тысячи.

Почти всё время будем смотреть на числа Фибоначчи: F(1) = F(2) = 1, F(n) = F(n − 1) + F(n − 2). Перебор аргументов разберём на функции, которая считает двоичные единицы.

---

**Прямая рекурсия может многократно вычислять одни и те же значения.** Рассмотрим последовательность F(1) = F(2) = 1; F(n) = F(n − 1) + F(n − 2), n > 2. Это одно из определений чисел Фибоначчи. Начальные значения: 1, 1, 2, 3, 5, 8, …

Прямая программа:

```python
def F(n):
    if n <= 2:
        return 1

    return F(n - 1) + F(n - 2)


print(F(5))
```

```output
5
```

Для вычисления F(5) возникают такие вызовы — левое дерево:

Это схема зависимостей вызовов, а не указание на их одновременное выполнение. Видно, что:

- F(3) вычисляется повторно;
- F(2) вызывается несколько раз;
- одинаковые подзадачи возникают в разных частях вычисления.

Без дополнительного сохранения результатов программа не знает, что такое же значение уже находилось ранее. Для этой реализации число вызовов быстро растёт:

| Что вычисляем | Общее число вызовов, включая первоначальный |
|---|---:|
| F(10) | 109 |
| F(20) | 13 529 |
| F(30) | 1 664 079 |
| F(40) | 204 668 309 |

При этом различных нужных значений для F(40) всего сорок: F(1), F(2), …, F(40). Отсюда естественная идея:

> Если значение уже найдено, сохранить его и при повторном обращении использовать готовый результат.

Такое запоминание результатов называют **мемоизацией**. Хранилище готовых результатов часто называют **кэшем**.

---

**Сначала посмотрим, как запоминание можно организовать явно.** Для хранения пар «аргумент — результат» в Python есть {{dict|словарь}}. Запись `memo = {1: 1, 2: 1}` означает: для ключа 1 сохранено значение 1, для ключа 2 — тоже 1. В нашем случае ключ — аргумент функции. Пройди программу по шагам и следи, как пополняется `memo`:

```python run memo.py
memo = {1: 1, 2: 1}


def F(n):
    if n not in memo:
        memo[n] = F(n - 1) + F(n - 2)

    return memo[n]


print(F(5))
```

```output
5
```

Проверка `n not in memo` означает, что результата для аргумента `n` пока нет. Если результата нет, вычисляем и сохраняем его. Если есть — **сразу возвращаем**: в пошаговом запуске второй вызов F(3) не спускается ниже. Так же быстро программа найдёт и F(50).

Здесь запись `memo[n]` обращается к значению по ключу. В отличие от индекса списка, ключ словаря может быть, например, отрицательным числом или очень большим аргументом без необходимости выделять все промежуточные позиции.

---

**Python позволяет включить такое запоминание готовой конструкцией {{cache|`@cache`}}.**

```python
from functools import cache


@cache
def F(n):
    if n <= 2:
        return 1

    return F(n - 1) + F(n - 2)


print(F(50))
```

```output
12586269025
```

Строка `from functools import cache` подключает готовое средство запоминания. Запись `@cache` над определением функции добавляет к ней это поведение: **повторный вызов с тем же аргументом использует сохранённый ответ**. Правое дерево на схеме выше — это работа `@cache`.

Такая запись называется **декоратором**: она изменяет способ работы функции, не требуя переписывать её основную формулу. Альтернативная запись — `@lru_cache(maxsize=None)`; у `@lru_cache()` без указания размера по умолчанию сохраняется ограниченное число результатов.

Для задач с числовыми функциями это удобно: результат определяется аргументом и не меняется между вызовами.

Однако кэш хранит **уже полученные результаты**. Он не может заранее дать ответ для вычисления, которое ещё не завершилось. Поэтому **кэш не исправляет ошибочную рекурсию**, бесконечно вызывающую сама себя.

---

**Повторные вычисления и большая глубина рекурсии — две разные проблемы.** Первая проблема: программа много раз решает одинаковые подзадачи. Её устраняют сохранением результатов.

Вторая проблема: одновременно остаётся слишком много незавершённых вызовов. Например, F(2000) → F(1999) → F(1998) → … → F(1). Даже если каждое значение вычисляется только один раз, получается длинная цепочка ожидающих вызовов.

В Python существует {{reclimit|ограничение глубины рекурсии}}. При его превышении возникает ошибка `RecursionError`. Посмотреть установленное ограничение можно так:

```python
import sys

print(sys.getrecursionlimit())
```

```output
1000
```

Изменить его позволяет команда `sys.setrecursionlimit(5000)`. Но увеличение ограничения само по себе **не ускоряет алгоритм** и не устраняет повторные вычисления. Слишком большое значение ограничения также не является универсальным решением: допустимая глубина зависит от среды выполнения.

Для длинной зависимости от предыдущих аргументов часто удобнее таблица с циклом из подтемы 3.

Есть и другой приём: если функция кэшируется и все её зависимости ведут к меньшим аргументам, можно заранее вызывать её по возрастанию. Само F(2000) — число из сотен цифр, поэтому напечатаем только его длину:

```python
from functools import cache


@cache
def F(n):
    if n <= 2:
        return 1

    return F(n - 1) + F(n - 2)


N = 2000

for n in range(1, N + 1):
    F(n)

print(len(str(F(N))))
```

```output
418
```

Почему это помогает? При вычислении F(100) результаты F(99) и F(98) уже есть в кэше. Поэтому новая длинная цепочка не создаётся.

Вызов `F(n)` внутри цикла нужен ради заполнения кэша, даже если его результат отдельно никуда не присваивается.

Однако такой порядок подходит именно тогда, когда нужные зависимости уже вычислены. Для переходов к большим аргументам порядок будет другим.

---

**Размер аргумента сам по себе не определяет трудность вычисления.** Сравним две зависимости. Если функция обращается к F(n − 1), то для большого n цепочка может содержать почти n вызовов. Если она обращается к F(n // 2), то аргумент на каждом шаге уменьшается примерно вдвое.

Даже число порядка 10¹⁸ при последовательном делении на 2 превращается в ноль примерно за шестьдесят шагов. Поэтому для огромного аргумента иногда достаточно короткой рекурсии. Создавать список длиной 10¹⁸ в такой ситуации совершенно не требуется.

Для оценки решения полезно спрашивать:

- сколько различных значений понадобится;
- сколько раз вычисляется каждое;
- какова максимальная длина цепочки вызовов;
- насколько велики сами результаты.

Когда говорят, что табличное решение имеет сложность O(N), обычно имеют в виду, что число шагов пропорционально количеству вычисляемых значений N. Но арифметика с числами из тысяч цифр требует больше работы, чем арифметика с небольшими числами. Поэтому число итераций — важная, но не единственная характеристика времени выполнения.

---

**Когда спрашивают, сколько аргументов подходит, функцию вызывают для каждого аргумента по очереди.** Пусть F(0) = 0, F(n) = F(n // 2) + n % 2 при n > 0. Сколько чисел 1 ≤ n ≤ 63 удовлетворяют условию F(n) = 2? Прямое решение — перебор со счётчиком:

```python
def F(n):
    if n == 0:
        return 0

    return F(n // 2) + n % 2


count = 0

for n in range(1, 64):
    if F(n) == 2:
        count += 1

print(count)
```

```output
15
```

Аргументы здесь уменьшаются вдвое, поэтому каждый вызов короткий, а 63 вызова программа делает мгновенно. Что именно считает эта функция и почему ответ 15, можно понять и без программы — это разобрано в дополнительной подтеме 6.

---

**Поиск аргумента по заданному значению функции начинается с вопроса, что именно функция считает.** Допустим, требуется найти минимальное n, для которого F(n) = K. Если диапазон небольшой и задан явно, можно перебрать допустимые n по возрастанию. Первое найденное совпадение будет минимальным.

Если граница не задана, перебор удобно вести {{while|циклом `while`}}: он идёт, пока значение не подошло, и останавливается на первом подходящем n. Для той же функции найдём наименьшее n с F(n) = 5:

```python
def F(n):
    if n == 0:
        return 0

    return F(n // 2) + n % 2


n = 1

while F(n) != 5:
    n += 1

print(n)
```

```output
31
```

Две ловушки перебора:

- **нельзя произвольно объявить**, что достаточно проверить, например, числа до миллиона, если такого ограничения нет в условии;
- **нельзя прекращать поиск** при первом случае F(n) > K, пока не доказано, что функция дальше не уменьшается.

Мы уже видели пример, где F(4) = 6, F(5) = 4 (подтема 2). Для функции этого шага F(7) = 3, F(8) = 1. Поэтому поведение результатов нужно обосновывать.

---

**Значение функции и число её вызовов — разные характеристики алгоритма.** Пусть F(1) = 1; F(n) = 2F(n − 1) + 1. Тогда F(2) = 3, F(3) = 7, F(4) = 15.

Но для вычисления F(4) программа с одним вызовом `F(n - 1)` на шаге выполняет четыре вызова: F(4), F(3), F(2), F(1). Результат равен 15, число вызовов — 4.

Множитель 2 умножает возвращённое число. Он **не создаёт второй вызов** функции. А выражение `F(n - 1) + F(n - 1)` без кэша действительно запускает два одинаковых вычисления.

Для функции Фибоначчи, если считать все вызовы прямой реализации, можно ввести отдельную функцию C(n): C(1) = C(2) = 1; C(n) = 1 + C(n − 1) + C(n − 2). Единица учитывает текущий вызов. Например, C(5) = 1 + C(4) + C(3) = 1 + 5 + 3 = 9 — столько вызовов на левом дереве схемы.

Если задача спрашивает число вызовов, число выполнений команды или порядок вывода, нужно анализировать именно выполнение программы. Добавление кэша или замена двух вызовов одним меняет эти характеристики, хотя возвращаемое значение может сохраниться.

---

**Итого.**

- Два вызова себя на шаге без запоминания дают лавину повторов: 109 вызовов для F(10), 13 529 — для F(20).
- Запоминание — словарь `memo` или `@cache` над `def`: каждое значение вычисляется один раз.
- Глубина — отдельная проблема: `sys.setrecursionlimit`, прогрев кэша по возрастанию или цикл с таблицей.
- Подсчёт подходящих n — цикл со счётчиком; наименьшее n — перебор по возрастанию до первого совпадения, без придуманной границы и без остановки при F(n) > K.
- Значение и число вызовов — разные величины.
