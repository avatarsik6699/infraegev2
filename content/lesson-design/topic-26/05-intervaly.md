**Интервалы времени решают три разные задачи: выбрать больше всего непересекающихся мероприятий, измерить общее занятое время и найти наибольшую одновременную нагрузку.** Это задачи о мероприятиях в конференц-зале, о периодах работы и простоя, о процессах и запросах, о людях в офисе; мероприятия были и на основной волне экзамена.

Весь урок идёт на пяти интервалах: (1, 3), (3, 5), (5, 8), (9, 15), (12, 16). Обоснование жадного выбора обменом и словарь с `get` знакомы по прошлым подтемам.

---

**Максимальное количество непересекающихся мероприятий выбирается по времени окончания.**

У мероприятия есть начало и окончание: `(start, finish)`. Пусть следующее мероприятие разрешено начать в момент окончания предыдущего. Тогда мероприятия совместимы, если start следующего ≥ finish предыдущего, а если нужен перерыв P — если start следующего ≥ finish предыдущего + P.

Как выбирать? Среди доступных мероприятий берём то, которое **раньше заканчивается**: оно раньше освобождает зал и оставляет не меньше возможностей для следующих.

<figure class="plate-figure">
%%greedy_timeline([[1, 3], [3, 5], [5, 8], [9, 15], [12, 16]], picked=[0, 1, 2, 3])%%
<figcaption>Выбраны (1, 3), (3, 5), (5, 8) и (9, 15) — четыре мероприятия; (12, 16) начинается раньше окончания (9, 15) и не помещается.</figcaption>
</figure>

```python
meetings = [(9, 15), (1, 3), (12, 16), (5, 8), (3, 5)]
pause = 0
meetings.sort(key=lambda x: (x[1], x[0]))
selected = []
last_finish = None
for start, finish in meetings:
    if last_finish is None or start >= last_finish + pause:
        selected.append((start, finish))
        last_finish = finish
print(len(selected), *selected)
```

```output
4 (1, 3) (3, 5) (5, 8) (9, 15)
```

Первый показатель ключа — окончание. Почему первый выбор обрабатывается через {{none|`None`}}? Чтобы случайно не потребовать перерыв **до первого мероприятия**: перерыв по условию нужен между мероприятиями.

<details class="proof" markdown="1">
<summary>Доказательство выбора обменом</summary>

Пусть некоторое оптимальное расписание начинается с мероприятия A. Наш алгоритм выбирает мероприятие G, заканчивающееся не позже A. Заменим A на G. Все остальные мероприятия расписания останутся допустимыми: зал освободится не позже прежнего. Количество мероприятий не уменьшилось. После первого выбора рассуждение повторяется для оставшейся части дня.

</details>

**Выбор по раннему началу или по короткой длительности не работает — это видно на контрпримерах.**

Почему не по началу? Раннее мероприятие может занять весь день:

<figure class="plate-figure">
%%greedy_timeline([[0, 20], [1, 3], [3, 5], [5, 7]], picked=[0])%%
<figcaption>По началу выбирается (0, 20) — одно мероприятие, хотя можно провести три: (1, 3), (3, 5), (5, 7).</figcaption>
</figure>

Почему не по длительности? Короткое мероприятие может пересекаться с двумя длинными:

<figure class="plate-figure">
%%greedy_timeline([[0, 4], [4, 8], [3, 5]], picked=[2])%%
<figcaption>Самое короткое (3, 5) пересекается и с (0, 4), и с (4, 8): выбор его первым даёт одно мероприятие, а можно провести два.</figcaption>
</figure>

Значит, нам важно **освободиться раньше в абсолютном времени**, а не просто выбрать короткое мероприятие.

**Второй критерий последнего мероприятия находят после максимизации количества.**

Жадный алгоритм выбрал (1, 3), (3, 5), (5, 8), (9, 15) — четыре мероприятия. Но последнее можно заменить на (12, 16): количество останется 4, а перерыв между двумя последними увеличится до 12 − 8 = 4. Порядок решения:

1. Найти максимальное количество k.
2. Взять первые k − 1 мероприятий жадного расписания.
3. Узнать время окончания предпоследнего.
4. Среди допустимых последних мероприятий выбрать то, которое позже начинается.

Почему первые k − 1 можно оставить жадными? **Жадное построение позволяет закончить k − 1 мероприятий максимально рано.** Более раннее окончание предпоследнего только увеличивает возможный перерыв, а подходящим последним становится любое мероприятие, начинающееся после него. Если гарантировано хотя бы два мероприятия, продолжение программы выше:

```python
penultimate_finish = selected[-2][1]
latest_start = None
for start, finish in meetings:
    if start >= penultimate_finish + pause:
        if latest_start is None or start > latest_start:
            latest_start = start
print(len(selected), latest_start - penultimate_finish)
```

```output
4 4
```

`selected[-2]` — предпоследняя выбранная запись, `selected[-2][1]` — время её окончания. Обрати внимание: максимизируем **начало** последнего мероприятия; позднее окончание само по себе не гарантирует большой перерыв. Если мероприятий меньше двух, такого перерыва нет — этот случай определяется условием.

**Похожие вопросы решаются той же заменой последнего**: самое позднее окончание последнего мероприятия — наибольшее `finish` среди мероприятий, которые начинаются не раньше `penultimate_finish + pause` (здесь 16).

Если в файле даны начало и длительность, окончание считают сразу при чтении: `finish = start + duration`. Если при одинаковом начале нужно выбрать более длительное последнее мероприятие, добавляется ещё один критерий — `finish − start`; на перерыв он не влияет.

**Объединение интервалов применяется, когда нужно измерить общее занятое время.**

Это другой вопрос, чем выбор непересекающихся мероприятий. Пусть система работала в те же пять интервалов. Первые три образуют один непрерывный период (1, 8), последние два — (9, 16). Общая длительность работы (8 − 1) + (16 − 9) = 14.

Сначала сортируем интервалы по началу, затем храним последний уже объединённый интервал:

```python
intervals = [(9, 15), (1, 3), (12, 16), (5, 8), (3, 5)]
intervals.sort()
merged = []
for start, finish in intervals:
    if not merged or start > merged[-1][1]:
        merged.append([start, finish])
    else:
        merged[-1][1] = max(merged[-1][1], finish)
print(*merged)
```

```output
[1, 8] [9, 16]
```

Объединённые интервалы записаны списками `[start, finish]`, потому что мы изменяем правую границу: `merged[-1][1] = ...`. Почему используем `max`? Новый интервал может полностью лежать внутри предыдущего: после (2, 20) и (5, 8) правая граница должна остаться 20. Условие `start > merged[-1][1]` склеивает касающиеся интервалы: (1, 3) и (3, 5) — один период. Так и нужно, если в момент окончания работа ещё идёт или следующая начинается сразу.

Если нужен суммарный простой за период от 0 до `day_end`, считаем промежутки между объединёнными интервалами — продолжение программы:

```python
day_end = 18
cursor = 0
idle_count = idle_duration = 0
for start, finish in merged:
    if start > cursor:
        idle_count += 1
        idle_duration += start - cursor
    cursor = finish
if cursor < day_end:
    idle_count += 1
    idle_duration += day_end - cursor
print(idle_count, idle_duration)
```

```output
3 4
```

Учтены простой до первой работы (0–1), простои между работами (8–9) и простой после последней работы (16–18). Здесь предполагается, что все интервалы лежат внутри рассматриваемого периода.

<figure class="plate-figure">
%%greedy_timeline([[1, 3], [3, 5], [5, 8], [9, 15], [12, 16]], merged=True, load=True, end=18)%%
<figcaption>Пять интервалов, их объединение — периоды 1–8 и 9–16, и число работающих между соседними событиями: больше всего, 2, — с 12 до 15.</figcaption>
</figure>

**b − a — длительность** непрерывного промежутка времени от a до b, а **b − a + 1 — количество целых номеров** от a до b включительно. От 10:00 до 10:05 прошло 5 минут, а номера 10, 11, 12, 13, 14, 15 — это 6 номеров. Целочисленные значения времени не делают формулу длительности автоматически равной `finish - start + 1`.

**Для количества одновременно работающих объектов удобно рассматривать события.**

Пусть нужно узнать максимальную одновременную нагрузку и сколько времени она держалась. В каждый момент времени проверять все интервалы дорого. Но количество активных интервалов меняется только при начале и при окончании интервала. Такое изменение будем называть **событием**.

Для модели, в которой объект активен при start ≤ t < finish, записываем в `start` изменение `+1`, в `finish` — изменение `-1`. Эта модель называется полуинтервалом [start, finish): начало включено, окончание исключено. Изменения копим в словаре через {{dictget|`get`}} — в один момент может быть несколько событий:

```python
intervals = [(1, 3), (3, 5), (5, 8), (9, 15), (12, 16)]
day_end = 18
changes = {0: 0, day_end: 0}
for start, finish in intervals:
    changes[start] = changes.get(start, 0) + 1
    changes[finish] = changes.get(finish, 0) - 1

times = sorted(changes)
current = maximum = total_duration = 0
for i in range(len(times) - 1):
    current += changes[times[i]]
    duration = times[i + 1] - times[i]
    if current > maximum:
        maximum = current
        total_duration = duration
    elif current == maximum:
        total_duration += duration
print(maximum, total_duration)
```

```output
2 3
```

Сортировка словаря `sorted(changes)` даёт отсортированный список его ключей. Между двумя соседними моментами количество активных постоянно. Почему сначала меняем `current`, потом учитываем длительность? Потому что после событий в момент `times[i]` новое количество действует до следующего события. В момент 3 одно мероприятие заканчивается, другое начинается: общее изменение −1 + 1 = 0, и количество не меняется.

**Если нужен максимальный непрерывный период постоянной нагрузки, соседние участки с одинаковым количеством нужно объединять.** Сам факт событий на их границе ещё не означает изменения количества — момент с нулевым итоговым изменением просто пропускают.

---

**Окно наблюдения и включённые границы меняют события, а не сам алгоритм.**

Иногда нагрузку нужно найти только за часть суток — например, с 8:00 до 14:00, — причём интервалы, попавшие в окно частично, учитываются. Тогда каждый интервал **обрезают краями окна**: `start = max(start, low)`, `finish = min(finish, high)`, а если после этого `start >= finish`, интервал в окно не попал. Если в файле вместо начала или окончания стоит 0 со смыслом «процесс шёл с начала наблюдения» или «не закончился», его заменяют краем окна.

Если время считается целыми моментами и объект активен в оба крайних момента отрезка [start, finish], событие окончания ставят в момент `finish + 1`: в момент `finish` объект ещё работает. Сначала определяется смысл времени, затем порядок обработки событий.

Число отрезков, в течение которых количество не менялось, считают по моментам с ненулевым итоговым изменением. Для наших интервалов за период от 0 до 18:

```python
times = [t for t in sorted(changes) if changes[t] != 0]
points = [0] + times + [day_end]
lengths = [b - a for a, b in zip(points, points[1:])]
print(len(lengths), max(lengths), *times)
```

```output
7 7 1 8 9 12 15 16
```

Моменты 3 и 5 выпали: в них одно мероприятие заканчивается, а другое начинается. Отрезков постоянного количества семь, самый длинный — с 1 до 8.

---

**Итого.**

- Больше всего непересекающихся мероприятий — по раннему окончанию; по началу и по длительности есть контрпримеры.
- Второй критерий последнего мероприятия — после первых k − 1 жадных: позднее начало (перерыв) или позднее окончание.
- Занятое время и простои — объединение интервалов, отсортированных по началу; края периода считаются отдельно.
- Одновременная нагрузка — события `+1`/`−1` в словаре и проход по отсортированным моментам.
- Окно наблюдения обрезает интервалы, включённые границы сдвигают окончание на `finish + 1`; момент с нулевым изменением границей отрезка не считается.
