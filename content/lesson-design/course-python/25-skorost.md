Главная идея урока: **скорость программы определяется тем, как растёт число действий с ростом данных, а не мелкими сокращениями записи**. Опора — вложенные циклы, проверка `in` для списка и множества и число вызовов Фибоначчи из урока о рекурсии: здесь эти наблюдения складываются в один способ оценки.

Сквозной пример урока — список из `n` чисел: один проход по нему, все пары и проверки принадлежности.

---

**Временная сложность описывает, как растёт работа с размером входа.** Программа может давать правильный ответ на десяти элементах и быть непригодной для миллиона. Нужно оценить, сколько действий она выполняет при размере входа `n`.

**Временная сложность** описывает рост затрат при увеличении входа. Запись `O(n)` означает верхнюю оценку, пропорциональную `n` с точностью до постоянного множителя при достаточно большом `n`. На практике часто так называют характерный порядок роста конкретного алгоритма. Это не обещание времени в секундах.

Порядки роста удобно сравнить на одном размере входа. Каждая клетка шкалы — в тысячу раз больше предыдущей:

<figure class="plate-figure">

<figcaption>При ста тысячах элементов один проход — 100 тысяч действий, сортировка — около 1,7 миллиона, а все пары — 10 миллиардов. Удвоение n удваивает работу <code>O(n)</code> и учетверяет <code>O(n²)</code>. Перебор всех подмножеств, <code>O(2ⁿ)</code>, и перестановок, <code>O(n!)</code>, растут ещё быстрее: при 30 элементах подмножеств больше миллиарда, при 40 — больше триллиона.</figcaption>
</figure>

Такой разрыв важнее любых синтаксических сокращений.

Для пар с `i < j` их вдвое меньше — `n · (n − 1) / 2`: при 10 элементах это 45, при тысяче — 499 500, при ста тысячах — почти 5 миллиардов. Порядок от этого не меняется.

---

**Число шагов считают по реальным границам циклов.** Два вложенных цикла не всегда означают `O(n²)`. Если внутренний цикл всегда делает 10 шагов, общее количество — `10n`, то есть `O(n)`. Если оба проходят `n` элементов, получается `n²`. Если внутренний проходит только значения после `i`, число пар равно `n(n - 1) / 2`, но порядок всё равно квадратичный.

```python
n = 1000
steps = 0
for i in range(n):
    for j in range(i + 1, n):
        steps += 1
print(steps, n * (n - 1) // 2)
```

```output
499500 499500
```

Если переменная на каждом шаге делится на 2, после `k` шагов размер уменьшается примерно в `2 ** k` раз. Поэтому нужно около `log₂(n)` шагов. Логарифм здесь возникает из вопроса «сколько раз можно делить пополам», а не из специальной функции Python.

```python
n = 1_000_000
steps = 0
while n > 1:
    n //= 2
    steps += 1
print(steps)
```

```output
19
```

Миллион делится пополам до единицы всего 19 раз: 2¹⁹ ≈ 524 тысячи, 2²⁰ ≈ 1,05 миллиона.

---

**Стоимость скрыта и внутри отдельных операций.** Для обычных реализаций Python полезны такие ориентиры:

| Операция | Обычная оценка |
| --- | --- |
| `len(list)` и `list[i]` | `O(1)` |
| `x in list` | До `O(n)` сравнений |
| `list.append(x)` | В среднем по длинной серии операций `O(1)` |
| `list.pop()` | В среднем по серии операций `O(1)` |
| `list.pop(0)` | `O(n)` из-за сдвига |
| Срез длины k | `O(k)` времени и новой памяти |
| `sum`, `min`, `max` | `O(n)` прохода |
| Поиск в dict/set | Обычно `O(1)`, в худших случаях хуже |
| `sorted` | В худшем случае `O(n log n)` сравнений, иногда быстрее |

Эти оценки предполагают, что сами сравнения, хеширование и арифметика рассматриваемых элементов недороги. Для длинных строк, огромных целых или пользовательских объектов это дополнительная работа.

Сравнивать `a[i:i + k]` в цикле не бесплатно: каждый срез создаёт до `k` элементов. Повторно строить `set(a)` внутри каждого запроса тоже неудачно — множество нужно построить один раз.

---

**Память тоже растёт с данными, если их сохранять.** **Пространственная сложность** описывает память алгоритма. Проход по файлу с одним счётчиком может использовать почти постоянную дополнительную память. Чтение всех чисел в список требует памяти, растущей с их количеством. Словарь частот требует места по числу различных значений.

Генераторы помогают избежать промежуточных коллекций, но если конечная функция делает `sorted`, все элементы всё равно нужно собрать для сортировки. Рекурсия хранит незавершённые вызовы, а кэш — ранее вычисленные результаты; это тоже память.

---

**Время измеряют разностью показаний часов, но сначала улучшают порядок роста.**

```python
from time import perf_counter

start = perf_counter()
answer = sum(range(1_000_000))
elapsed = perf_counter() - start
print(answer, elapsed)
```

`perf_counter` даёт показания часов для измерения длительности; важна разность, не абсолютное значение. Вывод здесь не показан: время зависит от компьютера и каждый раз немного другое. Один запуск шумный: влияют другие процессы, прогрев и среда. Для небольших повторяемых фрагментов есть `timeit`. Сначала улучши порядок роста алгоритма, затем измеряй и уточняй узкие места.

---

**Итого.**

- Сложность — рост числа действий с размером входа, а не секунды.
- Один проход — `O(n)`, все пары — `O(n²)`, деление пополам — `O(log n)`.
- Шаги считают по реальным границам циклов: пары i < j — n(n − 1)/2.
- `x in list` — до n сравнений, `x in set` — обычно один шаг; `pop(0)` у списка — сдвиг всех элементов.
- Сохранённые данные, рекурсия и кэш занимают память; время измеряют `perf_counter`.
