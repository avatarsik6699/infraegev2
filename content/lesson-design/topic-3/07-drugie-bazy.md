**Дополнительный урок — для продвинутых.** Он для тех, кто хочет закрыть все возможные случаи задания 3: в задачах подборки встречаются базы о театре, мебели, начислениях, машинах и агротоварах, но на реальных экзаменах 2022–2026 годов задание всегда было о товарах и магазинах. Задачи основных подтем решаются без него.

**Любая база задания читается тем же порядком: что означает строка каждой таблицы, какие поля связывают таблицы и в какой таблице лежит каждое нужное значение.** Новыми бывают предметная область и место хранения данных — например, цена лежит не в операции, а в справочнике.

Пример — маленькая база театра из трёх таблиц: спектакли, тарифы с ценами билетов и продажи билетов. Вопрос:

> Сколько рублей выручено за детские билеты на драмы М. А. Булгакова по тарифу утреннего или вечернего летнего спектакля?

---

**Сначала по схеме выясняют, что означает строка каждой таблицы и какие поля связаны.** Схема базы театра:

Строка таблицы «Продажа билетов» — одна покупка: билеты на один спектакль по одному тарифу, причём в трёх полях записано, сколько взрослых, льготных и детских билетов куплено. Значит, вопрос «сколько детских билетов» — сумма поля «Детских», а не число строк. Таблица «Спектакли» — справочник с автором и жанром, «Цены» — справочник тарифов, и **цена билета хранится в нём, а не в операции**: у каждого тарифа три цены, по одной на категорию билета.

---

**Цену из справочника подтягивают по ключу тарифа и берут столбец своей категории билета.** Разложим вопрос, как в подтеме 3: автор и жанр — из «Спектаклей» по коду спектакля; тариф — из «Цен» по ID тарифа; детские билеты — поле G операции; цена детского билета — пятый столбец таблицы «Цены». ---

**ИЛИ внутри одного поля — это сумма по каждому варианту или признак с функцией `ИЛИ`.** «Утренний или вечерний летний» — два значения одного поля «Тариф». Одна `СУММЕСЛИМН` проверяет все свои условия одновременно, поэтому её считают для каждого тарифа и складывают — так сделано в строках 8–10. Другой способ — признак строки `=ЕСЛИ(И(H2="М. А. Булгаков";I2="драма";ИЛИ(J2="Утренний летний";J2="Вечерний летний"));1;0)` и сумма вкладов по нему. Шаблон `"*летний"` здесь не годится: он захватил бы и «Дневной летний».

---

**Если таблиц больше трёх, рассуждение продолжается по цепочке ключей.** Например, операция содержит артикул, таблица товаров содержит ID поставщика, а таблица поставщиков — город. Чтобы определить город поставщика товара из операции:

1. по артикулу найти товар;
2. из записи товара взять ID поставщика;
3. по ID поставщика найти запись поставщика;
4. из неё взять город.

Каждый шаг использует конкретную связь. В Excel это два столбца `ВПР`: первый по артикулу возвращает ID поставщика, второй ищет этот ID в таблице поставщиков. Не нужно пытаться сразу угадать город по названию товара — нужно пройти по данным. Схема базы данных в условии помогает увидеть, какие поля связываются.

---

**Таблица связей хранит пары объектов, и её строки — не объекты, а пары.** Встречается и другой вид организации — таблица, которая хранит сами связи между объектами:

| ID ученика | ID кружка |
|---|---|
| U1 | K1 |
| U1 | K2 |
| U2 | K1 |

Здесь U1 посещает два кружка, а кружок K1 посещают два ученика. Такую ситуацию называют связью **«многие ко многим»**; для её хранения удобно использовать отдельную таблицу связей. Если нужно посчитать учеников, нельзя считать все строки такой таблицы: U1 присутствует дважды. Если нужно посчитать посещаемые пары «ученик — кружок», строки как раз соответствуют таким парам. Это ещё раз возвращает нас к вопросу: что означает одна запись и какой объект требуется посчитать?

---

**Ключ справочника должен определять одну запись — иначе связь размножает или прячет записи.** В нашем примере у каждого ID магазина одна запись в справочнике, поэтому каждой операции соответствует один район. Но если по ошибке справочник содержит два совпадения для одного ID, при полном соединении одна операция может получить две связанные строки; если затем сложить её количество дважды, результат завысится. А `ВПР` обычно выберет одно совпадение, что тоже может скрыть неоднозначность справочника. Поэтому правило такое:

> Для получения одной характеристики по ключу этот ключ должен однозначно определять нужную запись.

Когда связь действительно предполагает много подходящих записей, нужно решить, что именно требуется: вернуть одну характеристику, сложить все связанные значения, проверить существование хотя бы одной связи или посчитать разные объекты. Одна формула поиска не заменяет все эти действия.

---

**Наличие на дату — это начальное наличие плюс все движения не позже этой даты.** Прирост между двумя датами — движения строго после первой и не позже второй. В базах о машинах и складах спрашивают, например, прирост наличия на конец 1 июня 2022 года по сравнению с концом 1 июня 2021 года. Начальное наличие при вычитании сокращается, как в подтеме 5: остаются поступления минус выдачи с датой больше 01.06.2021 и не больше 01.06.2022. Граница «на конец дня» включает этот день, а «на начало дня» — нет; от этого зависит, какая из граничных дат входит в расчёт.

---

**Итого.**

- Незнакомую базу читают по схеме: что означает строка, какие ключи, где лежит каждое значение.
- Цена может храниться в справочнике: `ВПР` по ключу тарифа, столбец — по категории; вклад — количество × цена.
- ИЛИ внутри одного поля — сумма по вариантам или признак с `ИЛИ`; шаблон может захватить лишнее.
- Цепочка таблиц — несколько `ВПР` подряд; таблица связей хранит пары; ключ справочника должен быть уникальным.
- Наличие на дату и прирост между датами — движения в нужном промежутке, граница — из условия.
