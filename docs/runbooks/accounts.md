# Change 140: аккаунты и серверный прогресс — архитектура и поведение

Этот документ описывает **реализацию в рабочей ветке Change 140**, а не факт выпуска в
production. Нормативные продуктовые ограничения находятся в [SPEC](../SPEC.md) §2.2, §3–6,
§8; подробности интерфейса — в [FRONTEND](../FRONTEND.md) §5; условия выпуска — в
[production runbook](production.md). Код и миграция остаются источником истины для фактического
поведения. Ниже сознательно разделены реализованный контракт, локальная проверка и то, что
ещё требует внешней настройки или выпуска.

## 1. Что получает ученик

Аккаунт необязателен. Без входа можно читать опубликованные материалы, открывать задачи и
получать проверку ответа. Но правильный ответ гостя **не сохраняется**: после обновления страницы
или ухода нельзя рассчитывать на восстановление результата. У вошедшего ученика правильное
решение записывается на сервере и отражается в уроках, каталогах и самостоятельной практике.
Вход не даёт авторских, операторских или платных прав.

Есть четыре способа входа: подтверждённая почта с паролем, VK ID, Яндекс ID и Telegram.
Пользователь может привязывать поддерживаемые внешние способы к уже открытому аккаунту и
отвязывать их, пока остаётся хотя бы один способ входа. Совпадение почты у двух провайдеров
**не** объединяет аккаунты. Переноса прогресса между аккаунтами нет.
Аккаунт, созданный только через провайдера, может добавить почту и пароль после повторного
подтверждения входа; метод включится только после перехода по письму. Занятый другим
аккаунтом адрес не привязывается и не приводит к объединению.

Страница «Аккаунт» показывает способы входа, повторное подтверждение через провайдера,
выход и удаление аккаунта. Удаление отзывает все сеансы и удаляет сохранённый прогресс.
Отдельно можно после подтверждения сбросить прогресс **одного выбранного урока**; это не
удаляет аккаунт, прогресс другого урока или самостоятельной практики.

## 2. Карта системы и границы доверия

```text
Браузер (публичный UI, cookie без доступа JS)
    │  same-origin /api, Origin + CSRF для изменений
    ▼
Nginx (TLS, лимиты /api/auth, маршрутизация, защита логов)
    ├── Web: SSR/клиент, формы, текущее представление сеанса и прогресса
    └── API: авторизация, проверка задач, запись/чтение прогресса
            │
            ├── PostgreSQL practice: account_*, progress_result, task, lesson_task
            ├── SMTP: письмо с одноразовой ссылкой (если настроен)
            └── VK / Яндекс / Telegram: временный code → проверенный subject
```

Сервер API — единственная сторона, которая решает, кто владелец данных и верен ли ответ.
Клиент не вправе объявить задачу решённой или передать `user_id` для записи прогресса: владелец
выводится из активной сессии. Клиент хранит лишь временное представление данных для UI; после
выхода или смены аккаунта оно очищается. Персональные API-ответы помечены `no-store`, чтобы
браузер/прокси не переиспользовали их для другого пользователя. Публичный SSR не вставляет в
общий HTML персональный прогресс.

В БД разделены `infraege_runtime` для публичного чтения, `infraege_app` для ограниченных
ученических операций и `infraege_import` для операторского импорта банка. Это не «роли ученика»:
пользовательский вход никогда не превращается в право редактировать банк задач.

## 3. Модель данных: почему таблиц несколько

```text
account_user (внутренний UUID, создан)
 ├── account_password (0..1: email, Argon2-хеш, время подтверждения)
 ├── account_identity (0..N: provider + проверенный subject)
 ├── account_session  (0..N: хеш секрета, expiry, revoke, recent-auth)
 ├── account_token    (0..N: хеш одноразовой ссылки, назначение, expiry)
 ├── account_provider_challenge (временный state/PKCE/nonce и браузерная привязка)
 └── progress_result (0..N: контекст + задача + версия правильного ответа)
```

Внутренний `account_user.id` стабилен независимо от почты или имени у внешнего провайдера.
`account_identity` имеет уникальность пары `(provider, subject)` и пары `(user_id, provider)`.
Тем самым одна внешняя идентичность не может принадлежать двум аккаунтам и один аккаунт не
получает две разные личности одного провайдера. Почта не является внешним идентификатором:
провайдер может её не передать, изменить или передать адрес без нужного нам подтверждения.
Профиль пока не хранит редактируемых пользовательских полей; отдельная таблица профиля была бы
пустой абстракцией.

Секрет сессии и токены писем в БД представлены хешем, пароль — Argon2-хешем. Сама cookie
содержит случайный секрет, но не JSON с правами и не пароль. Сеанс можно отозвать на сервере.
Внешние access-токены не становятся нашей долговременной сессией и не сохраняются в браузере.
Удаление `account_user` каскадно убирает способы входа, сеансы, токены и результаты. История
правильных результатов старой версии решения может оставаться в БД до удаления аккаунта, но
уже не показывается как текущий прогресс. Текст ответа, неправильные попытки и черновики в
`progress_result` не попадают.

## 4. Почта и пароль: полный жизненный цикл

```text
Регистрация → account_user + неподтверждённый account_password
            → одноразовый email_verify (30 минут) → SMTP-письмо
            → переход по ссылке → подтверждение email → можно войти
Вход        → проверка email + Argon2-пароля + подтверждения
            → новая собственная сессия/cookie (предыдущая cookie при входе отзывается)
Сброс       → запрос ссылки (одинаковый ответ независимо от наличия email)
            → password_reset (20 минут) → новый Argon2-хеш
            → отзыв всех старых сеансов → новый вход
```

Пароль при регистрации: 12–128 символов; при входе проверяется существующий пароль.
Email нормализуется без учёта регистра. Нельзя войти по неподтверждённой почте, даже зная
пароль: сообщение про подтверждение почты относится именно к **разрешению входа по email**.
Повторный запрос письма предусмотрен. Токен ссылки одноразовый, имеет назначение и срок
годности; подтверждение адреса и сброс пароля — разные операции.
Повторное письмо реально отправляется не чаще раза в 60 секунд и не более пяти раз за
скользящий час на адрес и тип письма. Эти ограничения проверяет сервер под блокировкой записи;
экранный обратный отсчёт лишь объясняет ожидание и не заменяет защиту. Неподходящий адрес
получает тот же нейтральный ответ, но письмо не отправляется. Ранее выданные ссылки остаются
действительными до срока годности или использования; при исправлении ещё не подтверждённого
адреса старые ссылки отзываются, чтобы ими нельзя было подтвердить новый адрес.

Сервер регистрации требует конфигурацию SMTP (`SMTP_HOST`, `MAIL_FROM` и при необходимости
учётные данные). При отсутствии настройки он отвечает 503: интерфейс сам по себе письма не
отправляет. При доступном SMTP сервер отправляет реальное письмо через TLS. Важно: запись о
неподтверждённой регистрации фиксируется **до** отправки; если SMTP в этот момент откажет,
клиент увидит 503, а пользователь сможет запросить письмо повторно. Запросы повторного
подтверждения и восстановления намеренно возвращают одинаковую формулировку для существующего
и отсутствующего адреса — это снижает раскрытие списка зарегистрированных почт. Доставка
зависит также от внешнего SMTP, DNS и настроек домена, которые код не может гарантировать.

Пароль не отправляется письмом и не хранится в открытом виде. Сброс пароля отзывает все
активные сеансы: украденная старая cookie после смены пароля не остаётся действующей.

## 5. Внешние провайдеры и привязка

```text
«Войти через ...» → API создаёт challenge (10 минут): state, PKCE, nonce,
                     browser-cookie, безопасный внутренний return path
                  → redirect к конкретному провайдеру
                  → провайдер возвращает code и state в callback API
                  → API сверяет одноразовый challenge + браузерную cookie
                  → обменивает code, проверяет ответ и subject
                  → ищет (provider, subject) или создаёт account_user
                  → выдаёт свою новую сессию и перенаправляет внутри сайта
```

Код делает серверный authorization-code flow; адреса провайдеров и callback строятся из
конфигурации, а не принимаются от браузера. Для VK и Яндекса subject берётся после обмена code
и запроса к их API; для Telegram проверяется подписанный ID token с использованием JWKS,
issuer, audience и nonce. `state` одноразовый, привязан к тому же браузеру отдельной HttpOnly
cookie; PKCE снижает риск подмены code. Callback после использования или истечения challenge
не должен создавать повторную сессию. Возврат допускается только на безопасный внутренний
путь, а не на внешний URL.

Для provider-only аккаунта `POST /api/auth/account/email-method` принимает адрес и новый
пароль при активном сеансе, корректных Origin/CSRF и недавней аутентификации. Пока адрес не
подтверждён, `account_password` не входит в список доступных способов входа и восстановление
пароля на него не отправляется. Адрес можно исправить до подтверждения: операция отзывает
старые ссылки, после чего отправляет новую с соблюдением почтового лимита. Уникальность email
проверяется в БД; конфликт не раскрывается в ответе (нейтральный 202), без изменения владельца или переноса прогресса.

`login` создаёт или открывает аккаунт по точному `(provider, subject)`. `link` начинается из
уже открытого аккаунта, требует недавнего подтверждения входа (10 минут), проверяет, что
аккаунт не сменился во время перехода к провайдеру, и запрещает захват идентичности, уже
привязанной к другому пользователю. `reauth` подтверждает **именно уже привязанную**
идентичность и обновляет доверие к сеансу. `unlink` также требует недавнего входа и не
позволяет убрать последний способ входа. Никакого «нашли тот же email — значит, это тот же
человек» нет: такое объединение могло бы передать чужой прогресс не тому пользователю.

Локальный код адаптеров и тесты не означают, что кнопки провайдеров уже работают с реальными
аккаунтами: для этого нужны зарегистрированные приложения у каждого провайдера, точные callback
URL, секреты и проверка реального согласования/ответов перед выпуском.

## 6. Сессия, CSRF и другие защитные слои

Собственная сессия живёт до 30 дней, если не отозвана раньше. В production cookie имеет
`__Host-` имя, `Secure`, `HttpOnly`, `SameSite=Lax`, путь `/` и не задаёт `Domain`; локальный
HTTP использует отдельное имя и не ставит `Secure`, чтобы localhost был тестируемым. Хеш
секрета cookie хранится в БД, проверяются срок и отзыв. Вход/подтверждение провайдера выдаёт
новую сессию, выход отзывает текущую, сброс пароля — все сеансы, удаление аккаунта — все
связанные с ним данные.

Мутации требуют точного `Origin` сайта. Аутентифицированные изменения дополнительно требуют
заголовок `X-CSRF-Token`, вычисленный сервером от секрета сеанса и серверного ключа и
полученный через `/api/auth/session`; HttpOnly cookie сама по себе не даёт злоумышленной
странице этот токен. `SameSite` — ещё один слой, но не замена проверке Origin/CSRF. Ответы
аккаунта/прогресса имеют `no-store`; auth-маршруты на Nginx отдельно ограничены по частоте.
Ошибки БД и внешнего провайдера не должны раскрывать токены, пароли или приватные ответы.

Различайте три независимых состояния:

| Состояние | Что означает | Для чего важно |
|---|---|---|
| Почта подтверждена | Ссылка `email_verify` успешно использована | Разрешён вход по email/паролю |
| Сеанс активен | Cookie найдена, срок не истёк, отзыва нет | Доступ к своему прогрессу |
| Вход подтверждён недавно | Новый вход/`reauth` в пределах 10 минут | Привязка/отвязка и удаление provider-only аккаунта |

Предыдущее сообщение в профиле про «подтвердить вход повторно» обозначало третье состояние,
а не подтверждение адреса. Именно из-за смешения этих понятий текст профиля уточнён.

## 7. Удаление аккаунта: обновлённый контракт Change 140

Удаление всегда требует активной сессии, корректных Origin и CSRF, а в теле запроса —
явного `confirmation: "DELETE"`. Сама кнопка открывает диалог с предупреждением о необратимом
удалении прогресса. Далее сервер выбирает доказательство личности **по наличию подтверждённого
почтово-парольного способа входа**:

```text
Аккаунт с подтверждённым email/паролем
  → диалог требует текущий пароль
  → API проверяет Argon2-хеш
  → нет/неверный пароль: 403, аккаунт, сеансы и прогресс остаются
  → верный пароль: удалить account_user и каскадные данные, очистить cookie

Аккаунт только с внешним провайдером
  → повторно войти через уже привязанного провайдера при необходимости
  → authenticated_at должен быть не старше 10 минут
  → старое подтверждение: 403, данные остаются
  → недавнее подтверждение + диалог: удалить и очистить cookie
```

Для email-аккаунта текущий пароль и есть свежая проверка, поэтому дополнительно требовать
«войти за последние 10 минут» не нужно. После неверного пароля диалог остаётся открытым,
показывает ошибку и позволяет исправить ввод. Это изменение сделано по обратной связи после
локального теста: ранее сразу после входа хватало текстового подтверждения, что оказалось
слишком легко спутать с подтверждением почты и случайно выполнить.

Пока **не** вводится пароль для аккаунтов только с VK/Яндекс/Telegram: у них его нет. Их
удаление сохраняет прежний сценарий недавнего входа через провайдера. У аккаунта с несколькими
методами, в том числе подтверждённой почтой, для удаления требуется текущий пароль. Удаление
не является «мягкой деактивацией»: резервные копии и внешние логи управляются отдельными
сроками хранения из политики и операционных процедур.

## 8. Прогресс: что именно считается решённым

Ключ сохранённого факта — `(user_id, context_kind, context_id, task_id,
solution_revision)`. Контекст бывает `topic_lesson`, `course_lesson` и `standalone` с
фиксированным `context_id=standalone`. Это нужно, потому что одна и та же задача может
встречаться в разных уроках, но решение в одном уроке не обязано отмечать другой урок
пройденным. Nullable-части ключа нет; уникальность и идемпотентность проще обеспечить в БД.

```text
Гость: POST /api/tasks/{id}/check
       → ответ верен/неверен + объяснение; записи прогресса НЕТ.

Ученик: POST /api/tasks/{id}/check-and-save
         → сессия + Origin + CSRF
         → проверка: задача в опубликованном выбранном уроке
           либо видима в самостоятельном каталоге
         → проверка ответа и solution_revision
         → верный: INSERT ... ON CONFLICT DO NOTHING в той же транзакции
         → { correct, saved, explanation, solution_revision }
```

Неверный ответ не записывается. Для устаревшей версии решения API возвращает 409 и просит
обновить задачу. Повтор верного запроса для той же версии безопасен: дубликата нет.
`correct` и `saved` — разные сигналы: UI не имеет права обещать сохранение при ошибке записи.
Просроченная сессия даёт 401, а не «тихий» переход к гостевой проверке. Ответ пользователя
используется для проверки, но его текст не остаётся в таблице прогресса.

`GET /api/progress` отдаёт только результаты владельца, подходящие **текущей** версии ответа,
неархивной задаче и действующей опубликованной связи урока либо видимости самостоятельной
задачи. Смена `solution_revision` убирает старый результат из актуальной проекции без
подмены истории. Числители/знаменатели в темах, курсах, уроках и практике строятся по текущим
опубликованным задачам и их результатам; отдельные синхронизируемые счётчики не нужны.
Гость видит приглашение войти и закрытое состояние прогресса, а не выдуманный «0 решено».

`DELETE /api/progress/{context_kind}/{context_id}` разрешён только для `topic_lesson` и
`course_lesson`, проверяет сессию/Origin/CSRF и удаляет факты **этого пользователя и этого
урока**. Интерфейс запрашивает подтверждение. Самостоятельная практика и другие уроки не
затрагиваются; обратного восстановления через кнопку нет.

Ранее накопленный браузерный прогресс намеренно не импортируется: он не имел доверенного
владельца и мог бы быть присвоен не тому аккаунту. Его старые ключи не используются как
источник истины. Статистики попыток, ручной отметки «пройдено», рейтинга, premium-доступа и
слияния прогресса пока нет.

## 9. Ошибки и эксплуатационная граница

| Ситуация | Ожидаемое поведение |
|---|---|
| Нет конфигурации SMTP при регистрации | 503 для любого адреса; письмо не отправляется |
| Настроенный SMTP отклонил письмо регистрации | Нейтральный 202 для любого адреса; новый токен отозван, повторную ссылку можно запросить позже |
| Нет конфигурации SMTP при повторном письме или восстановлении | 503 для любого адреса, без проверки существования аккаунта |
| Настроенный SMTP отклонил письмо при повторном запросе | Нейтральный 202 для любого адреса; новый токен отозван, интерфейс не обещает доставку, сбой виден в серверной диагностике |
| Адрес отсутствует при запросе восстановления | Нейтральный 202; существование аккаунта не раскрывается |
| Письмо уже запрашивали недавно или достигнут часовой лимит | Нейтральный 202 для публичного запроса; новое письмо не отправляется, UI показывает ожидание и путь к исправлению адреса |
| Неверный/просроченный токен письма | Не подтверждается адрес и не меняется пароль |
| Адрес для привязки уже используется другим аккаунтом | Нейтральный 202 без письма; аккаунты не объединяются |
| Флаг провайдера выключен или нет конфигурации | Старт, привязка, повторное подтверждение и callback недоступны; интерфейс показывает недоступный способ, локальные email/гостевые функции независимы |
| Нет/истёк сеанс | 401 на персональном API; UI не показывает старой персональной выдачи как гостевую |
| Недоступна БД | Ограниченная ошибка сервиса, а не фиктивный пустой прогресс |
| Ошибка после правильного ответа | Не заявлять `saved=true`, если транзакция не завершена |
| Неверный пароль при удалении | 403, диалог остаётся открыт, данные не удаляются |

Локальная реализация, миграции, API/UI/операционные тесты и автоматизированные браузерные
сценарии проверяют контракт в контролируемой среде. Это **не** подтверждает доставку письма
через реальный SMTP, работу реальных provider-app credentials, юридическую готовность или
production-релиз. До `ship --release` нужны конфигурация и проверка SMTP/провайдеров, точных
callback origin, секретов, резервной копии с изолированным восстановлением аккаунтов/прогресса
и все применимые пункты [чеклиста обработки данных](privacy-legal-checklist.md). Обычный
`/work` ничего не публикует и не переносит в production.

## 10. Почему такие границы

| Решение | Причина и сознательный компромисс |
|---|---|
| Необязательный аккаунт | Учебный материал и проверка доступны без барьера входа; только долговременный прогресс требует идентичности. |
| Собственный `user_id`, методы входа отдельно | Почта и внешние атрибуты меняются; стабильный владелец прогресса не зависит от конкретного провайдера. |
| Нет auto-merge по email | Без явного подтверждения можно ошибочно передать чужой аккаунт и результаты. Пользователь вручную привязывает метод из открытого аккаунта. |
| Серверный факт верного решения вместо browser storage | Один авторитетный источник, владелец и проверка ответа на API; цена — зависимость персонального прогресса от сессии и БД. |
| Контекст + версия в ключе | Одна задача в нескольких уроках независима; изменение правильного ответа требует нового решения. |
| Никаких текстов ответов/ошибочных попыток | Достаточно факта правильного решения; меньше персональных данных и проще удаление. |
| Отзывная cookie-сессия вместо долгоживущего токена у клиента | Сервер может сразу прекращать доступ, а JavaScript не читает cookie; нужна БД на персональных запросах. |
| Текущий пароль для email-удаления | Деструктивное действие защищено даже сразу после обычного входа; provider-only использует доступную ему повторную аутентификацию. |
| Additive-миграция и отдельная DB-роль | Старые публичные чтения остаются совместимы; права записи учеников не расползаются на импорт банка. |

## 11. Обработка персональных данных: граница технического контракта

Аккаунт обрабатывает минимально необходимые для него данные: адрес электронной почты,
стойкий хеш пароля, проверенный идентификатор провайдера (когда провайдер включён), хеши
сессий и одноразовых ссылок, а также факт корректно решённой задачи в её учебном контексте.
Введённый ответ и ошибочные попытки не становятся данными аккаунта. При регистрации API
требует отдельное явное подтверждение обработки данных и сохраняет для нового аккаунта
версию текста и серверное время подтверждения. Это техническое доказательство не заменяет
проверку правового основания, текста документа или полномочий представителя.

Удаление аккаунта удаляет текущие рабочие записи каскадно, но не делает уже созданные
зашифрованные резервные копии мгновенно изменяемыми. По действующей операции Restic они
удаляются по ротации: до 7 ежедневных, 4 еженедельных и 3 ежемесячных точек. Удалённые данные
не должны восстанавливаться обратно в production при обычном восстановлении: восстановление
всегда выполняется сначала в изолированную среду, а возврат в рабочую БД требует отдельного
операционного решения.

Юридические основания, публичные сведения об операторе, обработчики/получатели, права
несовершеннолетних, трансграничные передачи и уведомление Роскомнадзора не выводятся из
кода. Их текущий статус, конкретные обязанности владельца и стоп-условия описаны в
[чеклисте обработки данных](privacy-legal-checklist.md). На дату документа уведомление
Роскомнадзора по решению владельца отложено до отдельной работы после релиза; это не делает
срок уведомления соответствующим закону и не может быть выдано за закрытый риск.
