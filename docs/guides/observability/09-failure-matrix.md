# 9. Матрица отказов и порядок диагностики

Матрица отказов отвечает на четыре вопроса: что сломалось, что продолжает работать, какие Source
изменятся и что из этого может заключить оператор.

## Типовые отказы

### Сломан только Web

Публичная страница может не загрузиться, хотя API readiness всё ещё отвечает 200. Тогда
`uptime-http`, направленный на `/health/ready`, не обязан обнаружить поломку полного browser UX.
Внешний GitHub probe публичной страницы и Nginx/journal Events дают дополнительный сигнал.

Это сознательная слепая зона узкого readiness Check: готовность API не доказывает исправность всей
пользовательской страницы.

### Сломан API

Readiness становится critical, а статическая или SSR-часть Web иногда ещё может отвечать. Source
`uptime-http` может остаться `ok`, если получил корректный HTTP-ответ, но его Check будет плохим.
Nginx Events помогают увидеть upstream error.

### Сломан Nginx

Публичные Web, API и collector перестают быть доступны через обычный вход. Public uptime ломается,
но сами Umami, Beszel и host services на VPS могут продолжать работу. Новые Nginx access records
перестают появляться, а journal может содержать причину остановки.

### Недоступен весь VPS

Одновременно ломаются независимые пути: public uptime, оба SSH Source и все private Source. Если
workstation и core работают, множество одновременных `unreachable` указывает на общий VPS, сеть или
provider, а не на семь отдельных adapter.

### Сломан WireGuard или локальный tunnel

`journal-http`, `beszel-api` и `umami-http` становятся `unreachable`. Public uptime,
`host-metrics-ssh` и `fail2ban-ssh` могут оставаться `ok`. Это характерный рисунок private transport
failure.

### Сломан Umami

Проблема локализуется в `umami-http`; consented analytics перестаёт поступать или читаться. Public
приложение должно продолжать учебный сценарий, потому что analytics optional. Nginx aggregates всё
ещё показывают server traffic.

### Сломан Beszel

`beszel-api` становится `unreachable` или `error`, но прямые SSH host Metrics могут продолжать
обновляться. Продукт не зависит от Beszel для обработки запросов.

### Выключен sre-kit core

Останавливаются polling, push ingestion, alert evaluation, REST/WS и Dashboard. Target-side Umami,
Beszel, journald, fail2ban и приложение продолжают работу. GitHub probe остаётся единственным
независимым элементом этой связки, но покрывает только внешний HTTPS/TLS.

### Сломан traffic publisher

Новые `traffic.request_count` перестают поступать, а остальные Source продолжают обновляться.
Следует смотреть время последней точки, cursor и publisher logs. Passive push Source не следует
считать гарантированным dead-man monitor: без отдельного freshness rule последний статус может
оставаться `ok` после остановки producer.

### Сломан или отсутствует Notification channel

Telemetry и Alerts продолжают сохраняться и отображаться, но Telegram delivery нет. В текущем
dogfood snapshot канал вообще не настроен, поэтому отсутствие Telegram-сообщения не доказывает
отсутствие проблемы.

## Компактная матрица

| Отказ | Public uptime | SSH Sources | Private Sources | Продукт |
|---|---|---|---|---|
| Web | readiness может быть `ok` | `ok` | обычно `ok` | UX сломан |
| API | Check плохой | `ok` | обычно `ok` | частично сломан |
| Nginx | плохой/недоступен | обычно `ok` | обычно `ok` | публично недоступен |
| Весь VPS | недоступен | недоступны | недоступны | недоступен |
| WireGuard | `ok` | `ok` | недоступны | работает |
| Umami | `ok` | `ok` | только Umami плох | работает без analytics |
| Beszel | `ok` | SSH metrics `ok` | только Beszel плох | работает |
| sre-kit core | нет локального опроса | нет локального опроса | нет локального опроса | работает |
| publisher | `ok` | `ok` | pull обычно `ok` | работает |

## Принцип корреляции

Один красный Source чаще указывает на конкретный adapter, credential или внешний инструмент.
Несколько красных Source с общей зависимостью указывают на эту зависимость. Несколько независимых
путей, сломавшихся одновременно, повышают вероятность общего отказа VPS или сети.

Это эвристика, а не математическое доказательство. Всегда учитывайте время последней точки и то,
была ли локальная сессия вообще включена.

## Минимальный порядок диагностики

1. Проверьте публичную страницу и `/health/ready` отдельно.
2. Посмотрите не только цвет, но и время последнего обновления Source.
3. Найдите рисунок: один Source, все private, все SSH или вообще все пути.
4. Сравните независимые пары: SSH/Beszel, Umami/Nginx, local uptime/GitHub probe.
5. Откройте Source detail и затем journal/fail2ban Events.
6. Сформулируйте гипотезу до изменения production.
7. Исправляйте через канонический `infraegev2` runbook или CLI.
8. Дождитесь следующего сигнала и убедитесь, что Alert resolved, а данные снова свежие.

## Что теперь должно складываться в единую картину

```text
infraegev2 создаёт и хранит первичные факты
                  ↓
Sources определяют конкретные каналы
                  ↓
adapters переводят внешние форматы
                  ↓
sre-kit нормализует, хранит и сопоставляет
                  ↓
Dashboard объясняет, Alert фиксирует проблему
                  ↓
оператор исправляет через infraegev2
```

На этом базовая архитектурная картина собрана целиком. Следующий уровень изучения — не новые
компоненты, а практика: выбрать один реальный инцидент, пройти этот порядок диагностики и записать,
какие сигналы подтвердили или опровергли каждую гипотезу.
