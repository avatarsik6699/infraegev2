# 2. Четыре вида наблюдаемых сигналов

Наблюдаемая система сообщает о себе не одной универсальной сущностью. У разных фактов разная форма,
и от формы зависит хранение, отображение и оповещение.

## Check: состояние сейчас

Check отвечает на вопрос «в каком состоянии проверяемая цель?».

```text
uptime.http = ok
tls.cert_expiry = warning
```

У Check есть имя, время, статус и дополнительные детали. Это не обязательно число. Например,
публичный сервер может ответить, поэтому Source успешно сработал, но вернуть неправильный HTTP
status. Тогда сам Source доступен, а Check сообщает о проблеме цели.

## Metric: число во времени

Metric отвечает на вопрос «сколько?» или «насколько?».

```text
cpu.usage_percent = 37.2
disk.usage_percent = 64.1
traffic.request_count = 128
```

Metric состоит из имени, числового значения, времени и необязательных labels. Повторяющиеся точки
образуют временной ряд. Labels позволяют разделить одно измерение, например по `path`,
`status_family` или `container`.

## Event: отдельное произошедшее событие

Event отвечает на вопрос «что произошло?».

```text
fail2ban заблокировал IP
Nginx записал ошибку upstream
служба была перезапущена
```

У Event есть время, уровень, сообщение и labels. В отличие от Metric, событие не обязано регулярно
повторяться или иметь числовое значение.

## Log: подробная техническая запись

Log — наиболее детальный исходный рассказ системы. Обычно это строка или структурированная запись
из journald. В core-контракте `sre-kit` нет отдельного типа `log`: адаптер `journal-http` превращает
подходящие журнальные записи в нормализованные Event.

Это важное разделение:

```text
journald хранит подробный первичный журнал
             ↓ journal-http
sre-kit хранит нормализованный операторский Event
```

Поэтому `sre-kit` не становится полной копией journald и не обязан хранить каждый исходный байт.

## А где аналитика

Аналитика не является пятым базовым типом `sre-kit`. Браузер отправляет в Umami разрешённое
продуктовое событие, например `lesson_completed`. Адаптер `umami-http` получает агрегаты и отдаёт их
в core как Metric, например число событий с label `event=lesson_completed`.

Один факт может последовательно менять форму:

```text
действие пользователя → событие Umami → агрегированный счётчик → Metric в sre-kit
```

## Не путать два вида состояния

- Source status говорит, смог ли канал сбора получить и обработать данные.
- Check status говорит, в каком состоянии находится проверяемая цель.

Например, `uptime-http` может успешно подключиться к сайту и получить HTTP 503. Source тогда
остаётся `ok`, потому что сбор состоялся, а `uptime.http` Check становится `critical`.

## Контрольный вопрос

Куда отнести «CPU равен 92%», «API недоступен» и «fail2ban заблокировал адрес»? Соответственно:
Metric, Check и Event.
